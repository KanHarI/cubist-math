including PR #85, merged at 07:55 Israel time. The working tree was clean

**The project has a working experimental H1 language, with substantially
stronger correctness and development checks since yesterday's audit.**
The instruction-isolation defect is corrected; declared types have useful
inspection; acceptance coverage is checked against its tests; build freshness
and sanitizer reporting are enforced. Current local checks passed all 13
native test binaries and 145 selected JavaScript tests, including the full
3,804-declaration archive corpus.

**H1 is still experimental.** Its semantic review, several acceptance cases,
representation comparison and truncation migrations remain open. Completing
K2.3 means its experimental integration is delivered; it does not grant
default admission. The latest successful branch CI run predates this morning's
fixes and, particularly, the change that makes sanitizer reports fatal.

The active direction remains language features and their kernel support.
Broad library rebuilding and the Galois, real/complex analysis and RH tracks
remain paused. The next useful increment is to close H1's release obligations
while developing inference, shared matching services and small theory records.

## Friction, refactor opportunities and developer experience

The first part of each item records observed or reported friction. Suggested
follow-ups are recommendations, not additional defects established by this report.

### 1. Release evidence needs to follow the integrated revision — high priority

CI deliberately runs automatically only on PRs targeting `main`, plus manual
dispatch. The latest branch run is at `bef00e3`; HEAD includes subsequent
fixes. Furthermore, commit `d988f00` reports that the earlier sanitizer job
was green while four binaries emitted undefined-behavior reports. Its green
status therefore does not establish sanitizer cleanliness.

**Recommendation:** make a pinned integration run a routine part of each
release candidate or substantial merge batch. Record the SHA, build stamp,
commands, job links and actual outcomes together. Keep the existing branch
policy unless there is reason to change it. The next run should include the
fatal sanitizer behavior, full Node suite, browser checks, lint and archive
re-derivation. A small script that assembles this evidence would reduce manual
status updates and prevent a previous run from standing in for current HEAD.

### 2. Acceptance labels needed repeated review — high priority

The matrix checker initially counted itself as evidence and mishandled partial
ranges; review also found tests with weaker assertions than the stated cases.
Those issues are fixed in `d622fbc` and `88b05e5`. The current checker verifies
textual traceability; a test naming an ID cannot establish semantic coverage
by itself.

**Recommendation:** retain explicit assertions for each case and promote the
review's small matrix mutations into lasting checker fixtures: missing test
labels, invalid IDs, partial ranges and missing remainders. If maintaining the
Markdown parser becomes recurring work, store case/layer/partial-status data
once and render the matrix from it. Keep human review of “in substance” cases
and the mathematical obligations as separate gates.

### 3. Equality search and shared syntax are recurring sources of regressions

The isolation correction exposed missing eta cases, costly whole-term
normalization, nontermination when sharing was disabled, branch-local facts
cached too broadly and swallowed deadlines. PR #77 then addressed an
exponential comparison caused by irrelevant renaming context. These were
correctness and resource-accounting problems found through successive reviews.

**Recommendation:** use the existing seed runner and kernel-work counters for
every change to comparison or search moves; add minimized counterexamples to
deterministic regressions. Make each move's progress condition, cache lifetime,
budget and error propagation explicit. Reuse the existing
[syntax-graph helpers](https://github.com/KanHarI/cubist-math/blob/c2a8306ebc5d44b2287895719f647cafd8f8d267/lib/cubical/syntax-graph.mjs) where their semantics
fit, and require new traversals to state how scope affects memoization.

There is also a concrete structural refactor opportunity:
[the driver](../../web/cubical-instruction-driver.mjs) is 1,443 lines and mixes
scope handling, syntax derivation, signature support and equality search;
[instructions.c](../../kernel/src/instructions.c) is 2,252 lines. Extract
cohesive services incrementally as those areas change. Preserve the isolation
tests and repeat the call-graph audit whenever trusted helpers move. A large
reorganization before the remaining H1 fixtures would make review harder.

### 4. Matching has a second motive-construction path — high priority

[match.mjs](https://github.com/KanHarI/cubist-math/blob/c2a8306ebc5d44b2287895719f647cafd8f8d267/lib/cubical/match.mjs) constructs its own explicit or
expected motive, while [motives.mjs](https://github.com/KanHarI/cubist-math/blob/c2a8306ebc5d44b2287895719f647cafd8f8d267/lib/cubical/motives.mjs) already
provides scoped abstraction and generalization. Current recursion requires
other arguments to stay fixed, and proof-statement matching remains open.
This is a known implementation boundary, not a newly discovered failure.

**Recommendation:** make L2.2a's next slice integrate the shared motive/goal
service, with acceptance examples for varying recursive arguments and dependent
local hypotheses. Preserve expression matching, explicit path/squash clauses,
source locations and rejection of escaping variables. This refactor delivers
a user feature and reduces the number of scoping paths future H2 work must
maintain. Similarly, extract application elaboration from the 1,631-line
[translator](https://github.com/KanHarI/cubist-math/blob/c2a8306ebc5d44b2287895719f647cafd8f8d267/lib/cubical/translate.mjs) as L4.1a introduces holes and
constraints, rather than extending one method for every new feature.

### 5. The native build repeats work and tracks configuration less fully

During this report's native build, each executable recompiled the entire
kernel source list. [kernel/Makefile](../../kernel/Makefile) tracks source and
header timestamps but does not make the normal build depend on compiler/flag
identity. The sanitizer fix already acknowledges this issue by separating
sanitizer configurations; WASM has the stronger content-stamp mechanism.

**Recommendation:** compile shared native objects once per configuration, with
header dependency files, and key or invalidate the output directory when the
compiler or flags change. Verify that an unchanged build is a no-op and a
flag-only change rebuilds the affected binaries. This should shorten local
checks and make switching configurations dependable. Keep standalone tests'
freshness checks. A documented `check-fast` command for affected tests would
also save contributors from reconstructing the focused command below.

### 6. Current status is still mixed with historical instructions

The work plan now identifies packages and the H1 specification owns the
release checklist, which reduces duplication. Some resumption material still
requires careful reading: the [HoTT handoff](../tactical/hott-automation-handoff.md)
opens with a current summary but later retains an old “Next unfinished item”
that names now-delivered A5/A4 work. The
[complex-analysis roadmap](../roadmaps/complex-analysis-roadmap.md) still uses
legacy “univalence axiom” wording, whereas the current kernel and results
catalogue treat univalence as derived cubical computation.

**Recommendation:** give each handoff one current checkpoint and next package,
then mark older instructions explicitly as historical. Audit assumption prose
against checked dependency outputs. Link summaries to the authoritative
package row/checklist instead of copying detailed statuses. Finish D2.1's
checked H1 chapter: the winding fixture is evidence, but does not explain the
supported fragment, recursion restrictions or assumption refusal to a new user.

### 7. Proof verbosity needs both feature work and adoption

The [concision vision](../roadmaps/vision/mathematical-proof-concision.md)
records a checked experiment reducing a 28-line Galois equality argument to
four lines using existing `simpa`. It also identifies genuine missing
inference, induction-generalization and theory facilities. Source length
alone cannot distinguish these causes.

**Recommendation:** use a few such arguments as stable before/after acceptance
fixtures for L4.1, L2.2a and theories. Measure explicit arguments, routine
transports, proof size and checking work, while comparing public types,
assumptions and extension markers strictly. The recorded `simpa` experiment
did not run that migration comparison; doing so would turn it into reusable
evidence without resuming broad mathematical rebuilding.

## Suggested sequence from here

1. **Refresh integration evidence and make release obligations reviewable.**
   Run the full integration checks on the next pinned candidate, including
   fatal sanitizers on Linux. For K2.1, attach evidence and a review decision
   to D1, D4, D5, Lemma H2, critical pairs and relative canonicity. The
   specification's finite-level checklist remains the authority.
2. **Close the immediately testable H1 gaps.** Add K1 with tubes, K6 along
   `ua`, and the H1 randomized generators/properties for K10/K11. Write the
   checked H1 reference chapter alongside these examples. E4/E11 still need
   automatic clauses; G2/G4–G7 need K2.5; X1–X8 need K2.4a. Keep those
   dependencies visible rather than treating the matrix checker as completion.
3. **Deliver migration tooling before retiring primitives.** Implement K2.4a's
   translation and generative-signature comparison, mixed-tier refusal and
   cost record; build K2.5's exact ledger verifier. Preserve strict public-type,
   assumption and extension checks. Retire Nat only after its criterion passes;
   retain the H2-dependent truncation migrations as deferred obligations.
4. **Develop the independent language improvements in small increments.**
   L4.1a, then L4.1b/L4.4; integrate `match` with A5; add L2.5a/b and core
   L2.4 records. Automatic clauses consume the h-level solver. Specify the
   initial/free-model universal properties before L2.6 and `deriving universal`.
   Use the native-build and handoff improvements to shorten this work's feedback
   loop.
5. **Use small computational examples to validate derived interfaces.**
   Advance N0/N1 and finite views; add N2/N4 after inference. Require checked
   laws, visible obligations and closed evaluation examples. Keep mathematical
   rebuilding paused until it is explicitly resumed.
6. **Proceed to H2, then the H3 research gate.** Specify indices/companion
   representation, substitution, ABI, rollback, codec and inspection before
   implementation. Preserve H1 regressions. Use the small dependent interpreter
   as H3 acceptance; concrete Cauchy reals retain their separate mathematical
   roadmap. Old-checker deletion, trained search and H4/E1/E2 remain optional.
