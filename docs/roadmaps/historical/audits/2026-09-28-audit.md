# Work-plan audit — 2026-09-28

## Scope and conclusion

Baseline: `h1-signatures` at `02a57efe3dbf04143b5b126c82482958bfc78ca7`
(PR #71), with a clean working tree before this audit. This includes the merged
H1 driver, inductive declarations, matching and language-notation work. Reviewed
the language and kernel proposals, their implementation and tests, and the reals
roadmap. Complex analysis, Galois and RH are outside this audit's scope.

**The implementation has reached an experimental H1 language, substantially
beyond the roadmaps' summary status.** G0, the instruction driver, basic proof
ergonomics, goal infrastructure and fuel accounting are delivered. H1's six
instruction families, source declarations and a useful explicit expression
`match` are implemented. H1 has not cleared its mathematical review or migration
gates. Theories, general inference, automatic clauses, H2 and H3 remain ahead.

The overall sequence is reasonable: finish H1 and its language clients, develop
inference and core theories alongside it, then tackle indexed and genuinely
inductive-inductive declarations. Keeping mathematical rebuilding paused and
using a small H3 fixture is appropriate. The next work should be driven by the
remaining gates, rather than the outdated “First actions” list.

**Highest-priority finding:** the claimed separation from the old conversion
checker is incomplete. A public conversion query changes a later instruction's
acceptance through a shared cache. This is reproducible and should be addressed
before relying on the stated trust boundary or retiring old checker code. It
does not demonstrate an inconsistent theorem.

**Reals verdict:** the roadmap already adopts higher inductive-inductive Cauchy
reals at H3. Its construction choice is current; its normal-form, approximation
and completeness-interface promises need revision.

## 2. Planning and design findings

Severity describes impact on the plan: **high** affects a trust/release contract
or a foundational interface; **medium** affects sequencing or promised scope;
**low** is reporting drift. Open research obligations are distinguished from
demonstrated implementation defects.

### 1. High — the old conversion checker still crosses the stated trust boundary

[Kernel instructions](../../kernel-instructions.md#what-remains-of-the-term-checker),
lines 551–562, names only alpha equality, syntactic cumulativity and a pushout
bridge builder as trusted remnants. Two implementation paths contradict that
description:

- `Step(Whnf)` and `Step(Normalize)` call the reducers
  ([instructions.c](../../../../kernel/src/instructions.c), lines 1964–1967).
  Those call `ck_convertible` for Glue and pair eta
  ([term_normalize.c](../../../../kernel/src/term_normalize.c), lines 63, 73, 133).
  The conversion strategy is therefore transitively part of trusted reduction.
- Successful conversion comparisons enter the same memo table used by folded
  alpha equality. A success is reused across comparison modes
  ([term_conversion.c](../../../../kernel/src/term_conversion.c), lines 473–501).
  A public “untrusted” conversion query can consequently satisfy a later
  instruction's supposedly syntactic side condition without an equality
  judgement in its premises.

The appendix gives a public-API reproduction: the same `Apply` first rejects,
then accepts after `cc_kernel_convertible`. All its typing premises are derived
by instructions. The equality involved is valid beta equality; this establishes
history-dependent acceptance and incomplete certificate isolation, not a false
equality or a consistency failure.

**Correction:** separate syntactic and conversion memo evidence; make the
reducer's equality dependencies explicit and either justify them as trusted
operations or replace them with the intended instruction mechanism. Add a
regression showing that untrusted queries cannot change instruction acceptance.
Expand I1.2 beyond moving three helpers. Optional code deletion can wait;
correctness of the advertised boundary should be a current task.

### 2. High — H1's default-release checklist is inconsistent with its decided scope

[H1 specification](../../h1-signature-specification.md), lines 10–13, still requires
every instruction family to be classified into section 2.3's cases. But lines
534–540 and 1213–1216 explicitly defer the tier-parametric extension, whose proof
contains that classification requirement at lines 618–620. The header therefore
imports a deferred extension's review work into finite-level H1's release gate.

The short K2.1 gate also highlights D1/D4/D5 and Lemma H2 while section 4.5
additionally records the critical-pair check as open, D9 as argued, and
canonicity as an outline relative to an assumed baseline. “All questions
decided,” “approved for implementation” and “review complete” need distinct
statuses.

Full normalization and decidable conversion are explicitly unestablished in
section 4.5; checking still uses budgets. A canonicity fixture is not a proof of
those stronger properties.

**Correction:** publish one release checklist for the actual finite-level H1
fragment. Map every applicable section 4 obligation to evidence and a review
decision; explicitly defer the tier-parametric derivation walk. Do not remove
the extension flag merely because the implementation and examples pass.

### 3. Medium — the native-retirement promise exceeds the approved representation map

[Kernel roadmap](../../cubical-kernel-roadmap.md), lines 220–222, and the adopted
HIIT design describe retiring native Nat, sum, W and pushout after comparison.
The approved [H1 specification, section 7.4](../h1-history.md#74-retirement-criterion)
instead retires **Nat only**. Sum, W and pushout remain trusted for tier-1
arguments. Its section 7.2 also exhibits mixed-tier calls that have no image
under the finite-tier translation.

**Correction:** split K2.4 into finite-tier differential/migration work, Nat
retirement, and explicitly deferred wider retirement. State what happens to
mixed-tier programs at the source boundary. Existing archive compatibility
does not prove compatibility for all accepted programs. Preserve X7/X8 and the
remaining native implementation's tests.

### 4. High — the proposed generic universal-property type is not a valid contract

[Language proposal](../../inductive-language-features.md), lines 48–56, proposes
`(initial T → M) ≃ T.Hom(…)`. It conflates arbitrary carrier functions, model
records and structure-preserving maps. On the literal carrier-function reading
it is false: the initial monoid has a singleton carrier; maps to a two-element
monoid have two choices, while a monoid homomorphism must preserve the unit and
has one choice.

**Correction:** before L2.6/`deriving universal`, specify separate typed results:
contractibility/uniqueness of `T.Hom(initial.model, M)` for a fixed target model;
the free-model property relating homomorphisms to generator assignments; and
any maps-out characterization in terms of the appropriate constructor/clause
data. Higher theories need their specified coherence fields. The circle's
maps-out example does not justify one formula for every theory.

### 5. Medium — older automation prerequisites reintroduce dependencies the work plan removed

[HoTT roadmap](../../hott-automation-roadmap.md), lines 395–402, lists indexed and
companion motives under the service required before milestone 7's first release.
Read literally, that pulls H2/H3 clients into H1. Lines 677–679 also put the
h-level solver before that first release, despite the explicit/automatic match
split in work-plan L2.2a/b. Explicit clauses already work without that solver.

**Correction:** make the first explicit H1 release depend on its actual
single-sort motive/clause services. Attach indexed and companion motives to
L4.2/L5.1, and the h-level solver to automatic clauses. Keep general inference
an improvement to explicit matching, as the scheduling authority already says.

### 6. Medium — the language proposal promises H1 behavior excluded by its specification

Two contracts need reconciliation:

- `Torus2` with a boundary `trans(p, q) = trans(q, p)` is assigned to H1 in
  [the language proposal](../../inductive-language-features.md), lines 167–182.
  H1 section 1.4 forbids composition in boundaries. A live experimental probe
  rejects this example with the expected section 1.4/Q3 diagnostic. A square
  torus is supported; the composite presentation needs a separately specified
  translation/equivalence or a later fragment.
- The same proposal, lines 207–220, promises proof-first `: set`/`: prop` and
  `set!`. Current H1 modifiers generate a squash constructor, and the current
  lowering has no proof-first pass. The later optimization changes the admitted
  signature and available clauses, so it needs more than an editorial label.

**Correction:** mark the actual H1 subset, assign proof-first h-level handling
to a package with path-characterization/h-level dependencies, and define its
signature and migration behavior. Do not change the kernel to accept examples
that the approved fragment deliberately excludes.

### 7. Medium — migration and integration evidence have unscheduled gaps

[H1 section 6.4](../../h1-signature-specification.md#64-the-kernel-extension-h1-marker)
says the migration verifier compares extension markers. The actual
[verifier](../../../../tools/proof-migration.mjs), lines 196–197 and 225–226,
compares `axioms`; it has no comparison of `extensions`. H1 provenance is not an
axiom, so that check cannot establish the stated contract. The specification's
representation translation and G2 exception ledger also still need tooling.

The H1 acceptance table includes randomized restriction/transport tests K10/K11
(specification lines 1960–1961). The current signature tests contain useful
fixed examples, including higher cubes, but this audit found no corresponding
randomized H1 generator. The existing randomized level tests cover G0 instead.

Finally, [CI](../../../../.github/workflows/ci.yml), lines 2–9, intentionally runs
automatically only for PRs into `main`; integration into `h1-signatures` is not
an automatic CI event. A feature merge alone is not evidence for the complete
integration gate.

**Correction:** give K2.3/K2.4/K2.5 explicit verifier deliverables, and maintain
an acceptance-ID-to-test matrix with missing cases visible. Record a complete
integration run against a pinned branch revision, through manual CI or an
appropriate branch trigger. The audit's archive run is baseline coverage; it
does not run X4 with declared replacements.

### 8. Medium — H2/H3 cannot be planned as only widening an admission gate

[HIIT design](../../higher-inductive-types-design.md), line 293, says the code is
the same at every stage and only the signature gate widens. That is a reuse
goal, not the current implementation contract: ABI 3 represents one sort,
parameters/recorded levels and one eliminator motive. Indices, varying-index
composition, dependent companion sorts and joint motives require further
representation and computation work.

**Correction:** make ABI, substitution, rollback, codec, inspection and
cross-stage regressions explicit deliverables of K4.2/K5.2. Keep H3's small
dependent context/type interpreter and reviewed research result as its gate.
Ordinary mutual data or the implemented one-sort circle do not test H3.

### 9. Low — duplicated summaries and next actions obscure actual progress

The work-plan summary still lists user declarations and all H stages as open,
H-stage markers as missing, and quick-reference work as remaining, while its
detailed rows record their progress. Its “First actions” still schedules fuel,
projections, module resolution and coverage reporting that are delivered. The
kernel/HIIT/language proposal headers and both documentation indexes understate
experimental H1. The K2.3 row should distinguish delivered clause-type
consumption (`match.mjs:104–105`) from unfinished inspector display.

[kernel/README.md](../../../../kernel/README.md), lines 65–69 and 80–108, is more
serious documentation drift: it describes pre-G0 specialization and the old
checker as the final checking API.

**Correction:** update the summary, detailed rows, indexes and handoffs in one
status pass. Use separate fields for implemented, experimental, review pending,
migration pending and deferred. Record the baseline revision. Retain the useful
statement about the motive service's missing client; it is still true.

## 3. Reals: what is current and what needs correction

### What is already aligned

The [reals roadmap](../../reals-roadmap.md) correctly chooses
`Real = initial CauchyStructure`, with a set carrier and proposition-valued
closeness relation, at H3. This is a genuine dependent companion-sort use.
H1 truncation or an ordinary quotient of Cauchy sequences does not supply it.
Dedekind reals remain a plausible fallback with less kernel work.

The roadmap is also explicit that mathematics is paused. The current work plan
replaces Cauchy reals/√2 as the active H3 release gate with a small interpreter;
the mathematical example remains deferred integration acceptance. No concrete
rational ordered field or complete ordered field has been constructed in the
rebuilt library. The archive itself records that its abstract `Q` and its
candidate real carriers did not supply those certificates.

### 10. High — the retained completeness interface has an unproved compatibility obligation

The roadmap says the interface “stays,” but
[complete_fields.cubist](../../../../archive/first-library/complete_fields.cubist),
lines 26–35, requires an actual natural-number bound for **each positive element
of the field carrier**, both for Cauchyness and convergence. The proposed HIIT
uses positive-rational precision. These are different constructive APIs; a
selector from arbitrary real precision must not be assumed to follow from
merely existing rational bounds.

**Correction:** R2 should choose positive-rational or natural precision for its
computational modulus, prove the sequence/HIIT-approximation bridge, and state
which legacy interface adapters require extra data. The HoTT book uses
positive-rational moduli. This is an unproved compatibility obligation, not a
claim that the archive's parameterized definitions fail to check.
[Source: HoTT book, real-number chapter](https://github.com/HoTT/book/blob/master/reals.tex#L437-L450).

### 11. Medium — real normal forms and approximation readout are overpromised

The reals table and rationale (lines 24 and 30) promise `rat`/`lim` constructor
normal forms only. The adopted design's “What computes” section explicitly
allows formal compositions. Data canonicity does not give a canonical rational
representation of an arbitrary real.

The fallback row also says approximations compute once truncation does. Native
truncation alone does not implement L2.9b or prove an approximation theorem.

**Correction:** promise constructors plus the stage's formal Kan forms, and
closed rational approximations obtained from a proved approximation result.
Require L2.9b, a closed computable input, and a checked error certificate. There
is no general source-level selector `Trunc(A) -> A`.

For readout's later H3 extension, specify the target type of the extracted
witness. Under heterogeneous transport a base witness has type `A(0)`, while
the requested result needs `A(1)`. The older design's “read off the base” needs
that case. H1's revised design uses homogeneous `hcomp` and computing parameter
transport, so this is not a demonstrated H1 runtime defect. Include transported
truncations in L2.9b's tests and revisit the argument when H3's formal operations
are fixed.

### 12. Medium — “field operations by folding” hides substantial construction work

R3 should separately schedule rational embedding, closeness/order compatibility,
extension and uniqueness, field laws, Archimedean laws and completeness.
Multiplication and inversion need appropriate bounded/domain-restricted
extensions; they are not all supplied by one globally Lipschitz fold. The book
constructs square/multiplication using bounded extensions and inversion away
from zero. [Source: HoTT book, Cauchy-real arithmetic](https://github.com/HoTT/book/blob/master/reals.tex#L1487-L1577).

This missing breakdown matters for estimates: a working H3 eliminator is a
language milestone, while a `CompleteOrderedField` model is a mathematical
development with its own proof obligations.

### Recommended dependency corrections

| Reals package | Explicit dependencies and acceptance |
| --- | --- |
| R1 integers | L2.1/L2.2a, arithmetic/setness/decidable-equality proofs; L2.7 for alternate presentations. |
| R1 canonical rationals | L2.7 plus gcd, normalization correctness and uniqueness, arithmetic/order laws. A generic H1 set quotient is a separate presentation; the fixed-point canonical representation is not supplied by the quotient constructor. |
| R2 field interface | L2.4 core theories and h-level fields; settle precision/modulus types before porting clients. It does not require H3. |
| R3 Cauchy reals | K5.1/K5.2/L5.1, L2.6 initial/fold support, rational prerequisites and the construction proofs above; L2.9b for closed approximation readout. |
| R4 Dedekind fallback | H1 truncation and the supporting cut/field mathematics. A generic quotient is not intrinsically needed for cuts if rationals use canonical representatives. Readout has its own gate. |

Also correct three smaller ambiguities: use `PosNat` for denominators and
`PosRat` for precision; map numbers to B3.*, rationals/fields to B4.* and reals
to B5.*; state “no resizing” as the rebuilt foundation's requirement. The
archive's universe-lowering `FieldExists` remains until the G2 ledger's actual
migrations. Preserve the distinction between that legacy behavior and the
new universe-preserving truncation.

## Appendix: conversion-cache reproduction

Save the following as `/tmp/instruction-cache-audit.c`, then run from the
repository root:

```sh
cc -O0 -std=c11 -Ikernel/include -Ikernel/src kernel/src/*.c \
  /tmp/instruction-cache-audit.c -o /tmp/instruction-cache-audit
/tmp/instruction-cache-audit
```

```c
#include "cubical_kernel.h"
#include <assert.h>
#include <stdio.h>

static cc_term term(cc_kernel *k, cc_judgement_id id) {
    cc_judgement_info i;
    assert(cc_kernel_judgement(k, id, &i));
    return i.term;
}

int main(void) {
    cc_kernel *k = cc_kernel_new();
    cc_term l0 = cc_kernel_term(k, CC_LCONST, 0, 0, 0, 0, 0);
    cc_judgement_id u0 = cc_instr_universe(k, l0), nat = cc_instr_nat(k);
    cc_entry_id a = cc_instr_extend(k, u0, 100);
    cc_judgement_id id_type = cc_instr_lambda(k, a, cc_instr_variable(k, a));
    cc_judgement_id beta_nat = cc_instr_apply(k, id_type, nat);
    cc_entry_id x = cc_instr_extend(k, beta_nat, 101);
    cc_entry_id y = cc_instr_extend(k, nat, 102);
    cc_judgement_id arg = cc_instr_variable(k, x);
    cc_judgement_id fn = cc_instr_lambda(k, y, cc_instr_variable(k, y));
    assert(arg && fn && !cc_kernel_error(k)[0]);
    cc_judgement_id before = cc_instr_apply(k, fn, arg);
    printf("Apply before=%u error=%s\n", before, cc_kernel_error(k));
    assert(!before);
    cc_kernel_clear_error(k);
    bool conversion = cc_kernel_convertible(k, term(k, beta_nat), term(k, nat), 10000);
    cc_judgement_id after = cc_instr_apply(k, fn, arg);
    printf("conversion=%d Apply after=%u error=%s\n", conversion, after, cc_kernel_error(k));
    assert(conversion && after);
    cc_kernel_free(k);
}
```

Observed at the audited revision:

```text
Apply before=0 error=The argument has the wrong type.
conversion=1 Apply after=9 error=
```

No explicit conversion judgement was supplied between the two applications.
Only this audit document is changed; the implementation findings are left for
separate fixes and review.
