Declaring a theory

A theory describes a kind of structure: the types it has, its operations and the laws they satisfy. A monoid, for instance, has one type, an associative multiplication and a unit:

import hlevels;

theory Monoid {
  sort M : set;
  mul(x, y : M) : M notation x * y;
  law mul_assoc(x, y, z : M) : (x * y) * z = x * (y * z);
  one : M;
  law one_mul(x : M) : one * x = x;
  law mul_one(x : M) : x * one = x;
}

A theory's body lists its fields, in order:

  • a sort, sort M : set; or sort P : prop;, is a type of the structure. Its evidence of being a set or a proposition is a field too, M_is_set : IsSet(U, M) or P_is_prop : IsProp(U, P), so a module that declares sorts imports hlevels;
  • an operation, mul(x, y : M) : M, or a constant, one : M, may have a notation: one of the operators x + y, x * y, x < y and x <= y, written with the operation's two arguments in order;
  • a law, law name(binders) : statement;, states a property of the earlier fields. A law must be a proposition: an equation between elements of a sort (sorts are sets or propositions), Void, or forall, -> and and over those, such as zero = one -> Void. A law holds no data, so law point : M; is refused: declare it as a constant.

Each field is in scope by its name after it is declared, and inside the theory a notation means its operation: x * y there is mul(x, y). The words sort, law and notation are keywords only in a theory's body.

Models

A model of a theory is a structure of its kind: a value for each field. Its type is Monoid.Model(U), for models whose sorts are in the universe U, and Monoid.make builds one, field by field. The natural numbers with addition are a monoid:

import nat;
import hlevels;

theory Monoid {
  sort M : set;
  mul(x, y : M) : M notation x * y;
  law mul_assoc(x, y, z : M) : (x * y) * z = x * (y * z);
  one : M;
  law one_mul(x : M) : one * x = x;
  law mul_one(x : M) : x * one = x;
}

def additive : Monoid.Model(U0) := Monoid.make(
  M := Nat, M_is_set := nat_is_set, mul := add, mul_assoc := nat_add_assoc, one := 0,
  one_mul := nat_zero_add, mul_one := nat_add_zero
);

def two_plus_three : additive.mul(2, 3) = 5 {
  rfl;
}

For a model m, m.f is its field f: additive.M is Nat and additive.mul(2, 3) computes to 5. A field's type is written through the earlier fields of the same model, so m.one_mul has type forall x : m.M. m.mul(m.one, x) = x, and goals and messages show fields this way. m.f is the projection Monoid.f(m), a definition like any other.

A parameter whose type is a theory's models makes a statement about every structure of that kind, in a universe of your choice:

import hlevels;

theory Monoid {
  sort M : set;
  mul(x, y : M) : M notation x * y;
  one : M;
  law one_mul(x : M) : one * x = x;
}

def one_one(U < UU0, G : Monoid.Model(U)) : G.mul(G.one, G.one) = G.one {
  exact G.one_mul(G.one);
}

Opening a model: open

open m; is a proof statement. For the rest of its block, each field of the model m is in scope by its name, and each notation of its theory means m's operation:

import hlevels;

theory Monoid {
  sort M : set;
  mul(x, y : M) : M notation x * y;
  one : M;
  law one_mul(x : M) : one * x = x;
}

def square(G : Monoid.Model(U0), x : G.M) : G.M {
  open G;
  exact x * x;
}

def square_one(G : Monoid.Model(U0)) : square(G, G.one) = G.one {
  open G;
  exact one_mul(one);
}

A name that open binds shadows the one it had, as let does, until the block ends, and a later open shadows an earlier one. Elsewhere, and in a declaration's statement, which is outside its block, + and * mean add and mul in scope, as for Nat. An operator means one thing in a scope, chosen by open, never by the types of its operands.

Sections

A section gives a group of definitions the same first parameters. Each parameter that is a model is opened for each definition's statement and proof, and inside the section a definition of the section is already applied to the section's parameters:

import nat;
import hlevels;

theory Monoid {
  sort M : set;
  mul(x, y : M) : M notation x * y;
  one : M;
  law one_mul(x : M) : one * x = x;
}

section {{U < UU0}}(G : Monoid.Model(U)) {
  def square(x : M) : M := x * x;

  def square_one : square(one) = one {
    exact one_mul(one);
  }
}

def additive : Monoid.Model(U0) := Monoid.make(
  M := Nat, M_is_set := nat_is_set, mul := add, one := 0, one_mul := nat_zero_add
);

def four : square(additive, 2) = 4 {
  rfl;
}

Inside the section, square(one) is square{{U}}(G, G.one); outside, square takes G first, and U in braces, and square_one states forall U < UU0. forall G : Monoid.Model(U). square{{U}}(G, G.one) = G.one. A recursive call passes the section's parameters unchanged too: in a section over G, power(x, k) inside power's own definition is power{{U}}(G, x, k). A section's parameters, in braces or not, come before each definition's own, so a definition in a section has no implicit parameters of its own, and no parameter of a section's name. A section holds definitions only, and sections do not nest.

Extension: extends

A theory can extend others. It has its parents' fields, in order, and then its own:

import hlevels;

theory Monoid {
  sort M : set;
  mul(x, y : M) : M notation x * y;
  one : M;
  law one_mul(x : M) : one * x = x;
}

theory Group extends Monoid {
  inv(x : M) : M;
  law inv_mul(x : M) : inv(x) * x = one;
}

theory CommMonoid extends Monoid {
  law mul_comm(x, y : M) : x * y = y * x;
}

theory CommGroup extends Group, CommMonoid {
}

def forget(G : CommGroup.Model(U0)) : Monoid.Model(U0) := G.group.monoid;

def same(G : CommGroup.Model(U0), x, y : G.M) : G.group.monoid.mul(x, y) = G.mul(x, y) {
  rfl;
}

A theory may extend several parents. An ancestor that two parents reach, as Monoid through Group and CommMonoid above, contributes its fields once, when it arrives with the same fields under the same names. A model of a theory has a model of each parent, by the parent's label: G.group, and then G.group.monoid. An unlabelled parent's label is its name in snake case: comm_monoid for CommMonoid. Each computes to the model built from the child's fields.

A parent can be labelled and its fields renamed, with a new notation for an operation. A semiring has two monoids on one sort, the additive one written with +:

import hlevels;

theory Monoid {
  sort M : set;
  mul(x, y : M) : M notation x * y;
  one : M;
  law one_mul(x : M) : one * x = x;
}

theory Semiring extends
    additive : Monoid(M := R, mul := add notation x + y, one := zero, one_mul := zero_add),
    multiplicative : Monoid(M := R) {
  law mul_add(x, y, z : R) : x * (y + z) = x * y + x * z;
}

def twice_plus(R : Semiring.Model(U0), x : R.R) : R.R {
  open R;
  exact x * x + x;
}

Renaming a sort to one name in two parents, as M := R twice above, makes it one sort of the child; its evidence follows it, as R_is_set. An ancestor that arrives renamed is another copy: here each monoid has its own unit, zero and one, and its own law.

Homomorphisms and isomorphisms

A homomorphism between two models of a theory, Monoid.Hom(A, B), is a map of their sort, map : A.M -> B.M, with, for each operation and constant, a proof that the map preserves it: map_mul and map_one. With several sorts there is a map for each, map_M, map_N. Laws need no field: they are propositions about sets. Monoid.Hom.make builds one, and f.map and the rest read it:

import nat;
import hlevels;

theory Monoid {
  sort M : set;
  mul(x, y : M) : M notation x * y;
  one : M;
  law one_mul(x : M) : one * x = x;
}

def additive : Monoid.Model(U0) := Monoid.make(
  M := Nat, M_is_set := nat_is_set, mul := add, one := 0, one_mul := nat_zero_add
);

def trivial : Monoid.Model(U0) := Monoid.make(
  M := Unit, M_is_set := prop_is_set(U0, Unit, unit_is_prop), mul := fun (x, y : Unit) => tt,
  one := tt, one_mul := fun (x : Unit) => unit_is_prop(tt, x)
);

def collapse : Monoid.Hom(additive, trivial) := Monoid.Hom.make(
  additive, trivial, map := fun (n : Nat) => tt, map_mul := fun (x, y : Nat) => refl(tt), map_one := refl(tt)
);

def unit_into(B : Monoid.Model(U0)) : Monoid.Hom(trivial, B) := Monoid.Hom.make(
  trivial, B, map := fun (x : Unit) => B.one, map_mul := fun (x, y : Unit) => sym(B.one_mul(B.one)),
  map_one := refl(B.one)
);

def round : Monoid.Hom(additive, additive) := Monoid.Hom.compose(unit_into(additive), collapse);

evaluate round.map(7) expecting 0;

Monoid.Hom.id(A) is the identity and Monoid.Hom.compose(g, f) is g after f; on closed models both compute. A child theory's homomorphisms preserve its parents' operations too, and f.monoid is the homomorphism of the parent's models.

An isomorphism, Monoid.Iso(A, B), is a homomorphism each way, to and from, with the round trips on each sort: from_to : forall x : A.M. from.map(to.map(x)) = x and to_from. Monoid.Iso.id(A), Monoid.Iso.compose(g, f) and Monoid.Iso.inverse(f) are isomorphisms too. A field of a value that is not a name is read the same way: Monoid.Iso.inverse(f).to.map(x).

A theory has homomorphisms when each of its operations and constants takes and returns its sorts:

import nat;
import hlevels;

theory Indexed {
  sort M : set;
  power(x : M, n : Nat) : M;
}

def no_homs(A, B : Indexed.Model(U0)) := Indexed.Hom(A, B);  // Error: Indexed's models have no homomorphisms: its power takes or returns something other than a sort.

What a theory declares

A theory is checked as ordinary definitions, which it declares in its module, in this order. Each is inspectable by name, uses no assumption, and computes:

DefinitionWhat it is
T.Model(U < UU0) : next(U)The type of models whose sorts are in U: the type of pairs of the fields, in order
T.make{{U < UU0}}(…)The model with the given fields, one parameter for each, so that named arguments build a model field by field
T.f{{U < UU0}}(m : T.Model(U))For each field f, its projection, written m.f
T.p{{U < UU0}}(m : T.Model(U))For each parent labelled p, the model of the parent, written m.p
T.Hom(A, B), T.Hom.make, f.map …, T.Hom.id, T.Hom.compose, f.pHomomorphisms, when every operation takes and returns sorts
T.Iso(A, B), T.Iso.make, f.to …, T.Iso.id, T.Iso.compose, T.Iso.inverseIsomorphisms

The theory's name itself is not a term: its models are T.Model(U). The universes of a homomorphism's models, and the models themselves, are implicit in its operations: f.map and Monoid.Hom.compose(g, f) read them from the types of f and g.

What is refused

A field's name, and an operator's meaning, are each one thing:

import hlevels;

theory Twice {  // Error: Twice has two fields named one: give each its own name.
  sort M : set;
  one : M;
  one : M;
}

Two parents that give fields of one name refuse unless the field is one ancestor's, shared:

import hlevels;

theory Left {
  sort M : set;
  point : M;
}

theory Right {
  sort M : set;
  point : M;
}

theory Clash extends Left, Right {  // Error: Clash gets a field named M from both Left and Right: rename one, as in Right(M := …).
}

open takes a model, and m.f a field the theory has:

import nat;

def open_a_number(n : Nat) : Nat {
  open n;  // Error: open takes a model of a theory, such as m : Group.Model(U0); this is a value of type Nat.
  exact n;
}
