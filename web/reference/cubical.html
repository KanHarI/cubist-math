Cubical paths and pushouts

All Cubist proofs use the Cubical C kernel. A declaration marked “Not checked” has no native certificate.

In cubical type theory, a path p : x = y in A is a function from an abstract interval into A. Its value at 0 is definitionally x and its value at 1 is y. Many path proofs can therefore be written directly, as functions of an interval coordinate, instead of by path induction.

Interval introduces a coordinate inside the forms below. It is not a type in a universe and cannot be used as an ordinary function domain. Coordinates accept 0, 1, flip(i) (the reversal 1 − i), meet(i, j) (minimum) and join(i, j) (maximum).

def reverse_path(A : U0, x : A, y : A, p : x = y) =
  path(fun (i : Interval) => A,
       fun (i : Interval) => at(p, flip(i)));

path(family, body) binds a coordinate in both arguments and constructs a path. at(p, i) evaluates a path at a coordinate. PathP(family, left, right) states a dependent path type: at coordinate i, the path lies in the type family(i). Plain x = y is the case of a constant family. Each family/body is written fun (i : Interval) => ...; their binder names need not agree. The kernel checks the actual family and endpoints.

def reverse_again(A : U0, x y : A, p : x = y) : y = x {
  exact path i => p @ flip(i);
}

def naturality_square(A B : U0, f g : A -> B,
    H : (forall a : A, f(a) = g(a)), x y : A, p : x = y) :
  PathP(fun (j : Interval) => H(x) @ j = H(y) @ j, cong(f, p), cong(g, p)) {
  exact path j => path i => H(p @ i) @ j;
}

reverse_again is the same term as reverse_path above, with the family read from the goal. naturality_square fills a square whose sides are cong(f, p), cong(g, p), H(x) and H(y). The outer path j gets its family from the PathP goal. Each inner path i gets its family from the equality at j. The kernel then checks all four edges.

Dependent paths and transport

def move_in_fiber(A : U0, C : A -> U0, x y : A, p : x = y, v : C(x)) : C(y) {
  exact along C by p from v;
}

def section_path(A : U0, C : A -> U0, f : (forall a : A, C(a)), x y : A, p : x = y) :
  PathP(fun (i : Interval) => C(p @ i), f(x), f(y)) {
  exact apd_path(f, p);
}

def section_via_transport(A : U0, C : A -> U0, f : (forall a : A, C(a)),
    x y : A, p : x = y) :
  PathP(fun (i : Interval) => C(p @ i), f(x), f(y)) {
  over C along p by {
    exact apd(f, x, y, p);   // goal: transport(C, x, y, p, f(x)) = f(y)
  }
}

There are two standard ways to state that a dependent function respects a path. A PathP states it directly, as a path lying over p. The transported equality transport(C, x, y, p, f(x)) = f(y) states it in one fiber. apd_path produces the first; the older apd produces the second. over lets you prove a PathP goal by proving the transported equality, when that is easier. The family C is never inferred: the elaborator does not search for a family that fits.

Function extensionality: ext

def pointwise_path(A B : U0, f g : A -> B, h : (forall x : A, f(x) = g(x))) : f = g {
  ext x;
  exact h(x);
}

Cubical paths make function extensionality provable: path i => fun x => h(x) @ i is a path from f to g. ext x; builds that term. It works for dependent functions too, provided the function type is fixed, meaning the goal is f = g with f g : forall x : A, C(x). It uses no axiom, unlike the FunExt interface.

Composition

comp(fun (j : Interval) => A, at(p, i),
  face(i, 0, fun (j : Interval) => x),
  face(i, 1, fun (j : Interval) => at(q, j)))

comp fills from coordinate 0 to coordinate 1, starting at the supplied base. Optional walls have the displayed face syntax; their coordinate belongs to the outer scope. The kernel checks that the walls match the base and agree on overlaps. With no walls, this is transport. Picture a square with the base as its bottom edge and the walls as its sides. comp produces the top edge. This is how trans is built.

Interval and face formulas are kept in a normal form of joins of meets. Some compact formulas have exponentially large normal forms. Rather than exhaust memory, the checker refuses any expansion beyond 4,096 clauses or a fixed work budget, with a lattice budget error. Split such a proof into smaller named steps.

Pushouts

def P = Pushout(S, A, B, f, g);
// f : S -> A; g : S -> B
// push_left(P, a) : P
// push_right(P, b) : P
// push_path(P, s) : push_left(P, f(s)) =[P] push_right(P, g(s))

pushout_induction(motive, leftCase, rightCase, bridgeCase, value) eliminates a pushout. The motive is a type family over the pushout; the bridge case supplies a dependent path over each gluing path, with endpoints given by the two point cases. Constructor computations are checked in C.

Suspension(A) is the pushout of the two constant maps A -> Unit. north(A), south(A), and meridian(A, a) use its point and path constructors. Open the checked examples.

Suspensions

Suspension is derived from the kernel’s pushout type. Its operations are ordinary definitions in the suspension library. Import suspension_types to use them; click their names to inspect their definitions. Suspension(A) has points north(A) and south(A), and, for every a : A, a path meridian(A, a) : north(A) = south(A). The circle and puncture models build on these operations.

def Suspension(A : U0) = Pushout(A, Unit, Unit,
  fun (_ : A) => tt, fun (_ : A) => tt);
def north(A : U0) = push_left(Suspension(A), tt);
def south(A : U0) = push_right(Suspension(A), tt);
def meridian(A : U0, a : A) = push_path(Suspension(A), a);

suspension_induction(A, C, atNorth, atSouth, coherence, point) eliminates into a family C on the suspension. The coherence argument takes a : A and proves

transport(C, north(A), south(A), meridian(A, a), atNorth)
  = atSouth

The result has type C(point). suspension_meridian_beta(A, C, atNorth, atSouth, coherence, a) gives the propositional computation law on the meridian: dependent application of the constructed section to that path equals coherence(a). See the suspension examples and circle proof.
