A first proof

Every natural number has a greater one. As a type, the statement is forall n : Nat. exists m : Nat. lt(n, m): for every n there is an m with n < m. First define lt, and try it on two numbers:

import naturals;

// n < m: m is n plus a positive number, succ(k) for some k.
def lt(n, m : Nat) : U0 {
  exact exists k : Nat. succ(k) + n = m;
}

// 2 < 7: take k = 4, since succ(4) + 2 = 7.
def two_lt_seven : lt(2, 7) {
  exact (4, refl(7));
}

lt is a function that returns a type, so its value is a type in U0: lt(n, m) is the statement that n is less than m. A value of it is evidence: a number k together with a proof that succ(k) + n = m. This lt is written out to show exists at work. naturals has its own <, computed rather than existential; a note at the end of this section shows how to use it.

two_lt_seven proves lt(2, 7), which unfolds to exists k : Nat. succ(k) + 2 = 7. The pair (4, refl(7)) takes k = 4, and refl(7) is accepted as evidence because succ(4) + 2 computes to 7. Any other k fails, because succ(k) + 2 would compute to a different number.

The REPL at the bottom of this page checks Cubist one entry at a time. typeof shows the type of a term, and evaluate computes its value; unlike the directive, it needs no expected value. Here the REPL has the example above loaded:

> typeof lt;
Nat -> Nat -> U0
> evaluate lt;
fun (n, m : Nat) => exists k : Nat. succ(induction k as k1 return Nat { zero => n; succ h => succ(h); }) = m
> typeof two_lt_seven;
lt(2, 7)
> evaluate two_lt_seven;
(4, refl(7))

lt takes two numbers and returns a type in U0. Evaluating it unfolds every definition, + included. naturals defines + by recursion on its first argument: 0 + b is b, and succ(a) + b is succ(a + b). So succ(k) + n computes one step, to succ(k + n). Then k + n is stuck, because k is a variable, not a numeral. It stays as the recursion that defines it: induction k as k1 return Nat { zero => n; succ h => succ(h); } reads “if k is 0, the result is n; if it is a successor, the result is succ(h), where h is the result for its predecessor”. With a numeral in place of k, the recursion runs to the end: succ(4) + 2 computes to 7. The chapter on natural numbers and inductive types explains induction. Fork into REPL copies the session into the REPL bar, to continue it there.

The same idea works for every n: succ(n) is greater than n, with k = 0. That gives the statement:

import naturals;

def lt(n, m : Nat) : U0 {
  exact exists k : Nat. succ(k) + n = m;
}

// succ(n) is greater than n: take k = 0.
def lt_succ(n : Nat) : lt(n, succ(n)) {
  exact (0, refl(succ(n)));
}

// Every number has a greater one.
def exists_greater_number : forall n : Nat. exists m : Nat. lt(n, m) {
  intro n;                       // n : Nat
  exact (succ(n), lt_succ(n));   // the witness, and the evidence
}

lt_succ proves lt(n, succ(n)), which unfolds to exists k : Nat. succ(k) + n = succ(n). The pair (0, refl(succ(n))) takes k = 0, and refl(succ(n)) is accepted as evidence because succ(0) + n computes to succ(0 + n) and then to succ(n).

exists_greater_number is proved in a block. At every point in a block there is a goal, the type still to be proved, and a context, the names available and their types. At the start the goal is the whole statement and the context is empty.

  • intro n; takes the input of the forall and adds it to the context, as in chapter 1. The context holds n : Nat, and the goal becomes exists m : Nat. lt(n, m).
  • exact (succ(n), lt_succ(n)); gives a value of exactly the goal type: the witness succ(n), and the evidence lt_succ(n) : lt(n, succ(n)). It finishes the proof.

In the proof workspace, click the line number of a proof statement to see its goal and the names in scope. Open in workspace opens any example of this reference there, and the elaborator section below shows every step of this proof.

A proof is a value like any other. Evaluating one shows the term its block built:

> evaluate lt_succ;
fun (n : Nat) => (0, refl(succ(n)))
> evaluate exists_greater_number;
fun (n : Nat) => (succ(n), 0, refl(succ(n)))
> evaluate exists_greater_number(5);
(6, 0, refl(6))

exists_greater_number is a function: given n, it returns the witness succ(n) and the evidence (0, refl(succ(n))). The REPL writes the nested pair (succ(n), (0, refl(succ(n)))) as (succ(n), 0, refl(succ(n))): a tuple of three is a pair whose second component is a pair. Applied to 5, it gives the witness 6, with k = 0 and refl(6) as evidence that succ(0) + 5 = 6.

The same proof as a term

A proof block is a readable way to build a term. A proof of a forall statement is a function: given n, it returns the witness and the evidence. It can be written directly:

import naturals;

def lt(n, m : Nat) := exists k : Nat. succ(k) + n = m;

def exists_greater_number : forall n : Nat. exists m : Nat. lt(n, m) :=
  fun (n : Nat) => (succ(n), (0, refl(succ(n))));

Both forms produce the same kind of kernel term. The chapter on proof blocks describes every statement a block can contain.

A wrong proof is rejected with a message, and nothing is added. Here the witness is n itself, which is not greater than n: the evidence lt_succ(n) is about succ(n).

import naturals;

def lt(n, m : Nat) := exists k : Nat. succ(k) + n = m;

def lt_succ(n : Nat) : lt(n, succ(n)) {
  exact (0, refl(succ(n)));
}

def not_greater : forall n : Nat. exists m : Nat. lt(n, m) {
  intro n;
  exact (n, lt_succ(n));  // Error: Type mismatch: found lt(n, succ(n)), expected lt(n, n).
}

The library’s <. The lt of this section is not the order that naturals provides. There, n < m stands for isLt(n, m), which is succ(n) <= m, and <= is defined by computation: 0 <= m is Unit, succ(n) <= 0 is Void, and succ(n) <= succ(m) is n <= m. A comparison of numerals computes to Unit when it is true, so tt proves it, and to Void when it is false, so nothing does.

import naturals;

// 2 < 7 computes to Unit.
def two_lt_seven : 2 < 7 {
  exact tt;
}

// n < succ(n) is succ(n) <= succ(n), which computes to n <= n.
def lt_succ(n : Nat) : n < succ(n) {
  exact nat_le_refl(n);
}

def exists_greater_number : forall n : Nat. exists m : Nat. n < m {
  intro n;
  exact (succ(n), lt_succ(n));
}
> evaluate 2 < 7;
Unit
> evaluate 7 < 2;
Void
> evaluate exists_greater_number(5);
(6, tt)
import naturals;

def seven_lt_two : 7 < 2 {
  exact tt;  // Error: Type mismatch: found Unit, expected 7 < 2.
}

With a variable, the computation stops at the variable, so proofs about < use lemmas. nat_le_refl(n) : n <= n proves n < succ(n), because succ(n) <= succ(n) computes to n <= n. Both definitions describe the same order. The library’s gives short proofs by computation; the one in this section says what a proof contains.

The library’s < is defined by induction on natural numbers, which this chapter has not introduced yet. The chapter on natural numbers and inductive types returns to it: the order on natural numbers shows its definition and proofs about it by induction.

The elaborator

Cubist has two parts. The elaborator, written in JavaScript, reads the source and builds kernel terms: fully explicit terms, in which every function has typed parameters, every notation is expanded, and every proof statement has become part of a term. The kernel, written in C, then checks each term. Proof assistants call this first step elaboration rather than compilation. The elaborator adds detail to what you wrote, working out from the types what the source leaves implicit, and its output is never trusted: the kernel checks it again.

For the first proof, elaboration does four things:

  • Parameters become functions. def lt(n, m : Nat) : U0 { … } has the type Nat -> Nat -> U0, and its value is fun (n, m : Nat) => ….
  • Notation expands. + becomes add from naturals, exists a dependent pair type, = a path type, and numerals the kernel’s 0 and succ.
  • Proof statements build the term. Each statement faces a goal and builds part of the term. intro n; builds fun (n : Nat) => ?, and exact fills the hole ? with its value.
  • The kernel receives a graph of native nodes. Each node has an opcode, such as CC_LAM for a function or CC_PI for a function type. Two nodes come from the elaborator rather than the source: exact checks its value at the goal T by applying fun (ascription : T) => ascription to it, and refl(x) is the path that stays at x, CC_PLAM.

The kernel then checks the term one node at a time, applying one typing rule to each. Entering a binder checks that its domain is a type and extends the context with the bound name. An application checks its argument against the domain of the function’s type. Wherever a type must match another, the kernel compares the two by conversion, unfolding definitions such as lt as needed.

Open Elaboration below the first proof to see each of its declarations elaborated step by step. Its Kernel row shows the kernel’s check as a forward derivation, recorded by the kernel as it ran. Each step applies one rule, such as CtxExt to extend the context or PiIntro to build a function, to earlier steps, and a comment above it gives the judgement it derives. Steps the elaborator added, such as the ascription, are marked. For more info on the kernel and its opcodes, see the kernel reference, still to be written.

import naturals;

def lt(n, m : Nat) : U0 {
  exact exists k : Nat. succ(k) + n = m;
}

def lt_succ(n : Nat) : lt(n, succ(n)) {
  exact (0, refl(succ(n)));
}

def exists_greater_number : forall n : Nat. exists m : Nat. lt(n, m) {
  intro n;
  exact (succ(n), lt_succ(n));
}

What checking means

A declaration is accepted only when the kernel accepts its term at its stated type. Only the kernel has to be correct, and it is small: it checks the finished term, not the way the elaborator found it. So a bug in a convenience, such as notation, a tactic or simplification, cannot produce an incorrect proof, because whatever the elaborator builds must still pass the kernel. At worst, such a bug makes a correct proof fail to check, and a declaration that does not check cannot be used.

Each declaration is checked on its own. A rejected declaration is not added, so a later declaration that uses it fails too, with a message naming the missing dependency:

def wrong : Nat {
  exact Nat;  // Error: Type mismatch: found U0, expected Nat.
}

def uses_wrong := wrong;  // Error: Untranslated dependency: wrong

Here wrong fails because Nat is a type, not a number, and uses_wrong fails because wrong does not exist. The chapter on checking and inspection shows where to run the checker and how to read its results.

Files and imports

A source file has the extension .cubist. It starts with imports, followed by declarations and directives in any order:

import naturals;
import sets;

// Declarations and directives follow the imports.
def seven := 7;

An import names a module without quotes or a file extension. import naturals; loads naturals.cubist. The command-line checker looks first in the directory of the file being checked, then in the library: the rebuilt library under library/, then the archived first library. The imported module is checked too, along with everything it imports.

An import makes every checked declaration of the module available, and so do the modules it imports in turn. It also brings the simplification rules and sets that those modules register. Importing a module does not make a theorem depend on that module’s assumptions. Each theorem’s assumptions are computed from its own checked term.

Imports must come first. An import after a declaration is a syntax error:

def zero_again := 0;

import naturals;  // Error: Imports must come before declarations.

Names and comments

A name starts with a letter or an underscore, followed by letters, digits and underscores. Names are case-sensitive: value and Value are different names.

def value := 0;

def Value := 1;

Comments run from // to the end of the line. There are no block comments and no string literals. Source is plain ASCII: write ->, forall and exists, not arrows or quantifier symbols. The inspector can display mathematical symbols, but the source cannot contain them:

def arrow(A : U0) : A → A {  // Error: Unexpected character →
  intro a;
  exact a;
}

A name cannot start with a digit:

def 2nd = 0;  // Error: Expected a name.

Descriptions

// comments directly above a declaration become its description in the inspector, including when the declaration is imported. Consecutive comment lines join into one paragraph, and an empty // line starts another. A blank line separates a section comment from the declaration that follows it. A comment at the end of a line does not describe the next declaration. Descriptions are plain text and do not affect checking.

// Section: small functions.

// The identity on numbers.
//
// A second paragraph of the same description.
def same_number(n : Nat) := n;

Here the first comment is a section comment, because a blank line follows it. The next three lines are the description of next.

Declarations

A declaration names a checked term. Its value follows :=, and = always means equality. There are three main forms:

FormMeaning
def name(params) := term;The term form. The result type is inferred from the term. The parameters are optional.
def name(params) : T := term;The typed term form. The term is checked against the stated type T.
def name(params) : T { … }The block form. The block is checked against the stated result type T. Use it for proofs and for constructions whose type should be stated.
 
def identity_term(A : U0, x : A) := x;

def same(A : U0, x : A) : A {
  exact x;
}

def second_of_two(A : U0, x, y : A) : A {
  exact y;
}

A term declaration ends with ;. A block declaration ends with }. A short term with a stated type uses the typed term form, which means the same as a block with exact:

def four : Nat := 4;

def four_again : Nat {
  exact 4;
}

Writing = for := is an error. In def four : Nat = 4; the checker reads Nat = 4 as the type, an equation, so it says what to write instead:

// Error: Write := to give a value: def name : T := term; here `=` read as an equality type
def four : Nat = 4;
def seven = 7;  // Error: Write := to give a value: def name := term;

A missing semicolon is reported at the next token:

def one := 1
def two := 2;  // Error: Expected ';', found 'def'.

Other declaration forms

FormMeaning
computable def name …A definition that must use no assumption. See computability.
evaluate term expecting value;A directive that checks what a closed term computes to. See evaluate.
simp_rule name priority N;
simp_set name := [rule, …];		Directives that register checked equalities for simplification. See registering rules.

Parameters

A parameter list is a comma-separated sequence of typed binders. Consecutive parameters with the same type may share it: (A, B : U0, x, y : A) means (A : U0, B : U0, x : A, y : A). A later parameter’s type can mention earlier parameters, as x : A does.

def flip_arguments(A, B, C : U0, f : A -> B -> C) : B -> A -> C {
  intro b, a;
  exact f(a, b);
}

def pick_second(A, B : U0, x, y : A, b : B) := y;

def picked := pick_second(Nat, Nat, 1, 2, 3);

A declaration with parameters is a function of them. Every argument is written at each use: there are no implicit arguments, so pick_second takes both types explicitly, here Nat twice. Arguments can also be supplied a few at a time:

def first(A, B : U0, a : A, b : B) := a;

def first_number := first(Nat, Nat, 5);

def five := first_number(7);

first_number has type Nat -> Nat: it waits for the last argument. Supplying more arguments than a function takes is an error:

def pick_first(A, B : U0, a : A, b : B) := a;

def too_many := pick_first(Nat, Nat, 1, 2, 3);  // Error: Source application is not a function.

Every parameter needs a type. After x, the parser expects a colon, or a comma and another name sharing the type:

def untyped_parameter(x) := x;  // Error: Expected ':', found ')'.

Parameters or a quantified type

A statement can put its inputs in the parameters or in the result type. These two declarations have the same type, forall A : U0. A -> A:

def in_parameters(A : U0, a : A) : A {
  exact a;
}

def in_type : forall A : U0. A -> A {
  intro A, a;
  exact a;
}

Parameters are shorter. A quantified result type is better when the statement is a named proposition that other declarations reuse.

Order, scope and recursion

Declarations become available in source order. A declaration can use only the declarations above it and the imported ones. There are no forward declarations:

def uses_later := later;  // Error: Untranslated name: later

def later := 0;

A declaration cannot refer to itself, so there is no recursive definition. Recursion and induction use an eliminator instead, such as natural-number induction:

def loop(n : Nat) : Nat {
  exact loop(n);  // Error: Untranslated name: loop
}

Each name can be declared once in a module:

def twice_named := 0;

def twice_named := 1;  // Error: Definition symbol is already registered.

Inside a declaration, parameters and local names shadow outer ones. Choose fresh local names when a clash would be confusing to the reader.
