SYNTAX, MEANING, AND CHECKED EVIDENCE

Language reference

Write terms and proofs in dependent type theory. Cubist elaborates each declaration into instructions checked by the C kernel.

This page describes the mathematical .cubist language. The kernel workbench shows checked terms, their context, and native opcode assembly.

One principle runs through the whole language. The elaborator is written in JavaScript and may be arbitrarily clever: it expands notation, finds rewrite positions and chooses simplification rules. It is not trusted. Everything it produces is an ordinary kernel term, and the C kernel checks every one of them. A convenience that the kernel cannot check makes the declaration fail. It never becomes an assumption.

A first proof

def identity : forall A : U0, A -> A {
  intro A;       // A : U0
  intro value;   // value : A
  exact value;
}

A theorem proves its stated type by constructing a term of that type. Here the term is a function: given a type A and an element of it, return that element. No axioms or imports are needed.

At any point in a proof block there is a goal, the type still to be proved, and a context, the names available with their types. At the start the goal is the whole statement and the context is empty. intro takes the next input from the goal and adds it to the context. After intro A; the goal is A -> A and the context holds A : U0. After intro value; the goal is A and the context also holds value : A. exact value; supplies a term of exactly the goal type and finishes the proof.

The same proof can be written as a single term, def identity(A : U0, value : A) = value;. Blocks and terms are interchangeable: a block is a readable way to build a term. In the proof workspace, click a proof-step line number to see its goal and context.

Files and names

import paths;
import sets;

// Declarations and simplification directives follow the imports.

Imports come first and use module names without quotes or a file extension. import paths; loads paths.cubist from the proof library. The CLI first looks in the directory of the file being checked. Imported source and its dependencies are checked too. An import brings in every checked declaration of that module, along with the simplification rules and sets it registers. An import alone does not make every theorem depend on all of the imported module's axioms: each theorem's dependencies are computed from its own checked derivation.

Names are case-sensitive: a letter or underscore, followed by letters, digits, or underscores. Write comments with // through the end of the line. Block comments, quoted strings, and Unicode operators are not source syntax. Use ->, forall, and exists; the inspector can display mathematical symbols.

Put // comments immediately above a declaration to show them as its inspector description, including through imports. Consecutive lines are joined into a paragraph; an empty // line starts another paragraph. A physical blank line separates a section comment from a declaration. Trailing comments do not document the next declaration. Descriptions are plain text and do not affect the checked proof.

Declarations become available in source order. There are no forward declarations and no implicit arguments: every argument is written at each call. Choose fresh local names to avoid collisions with names already in scope.

Parameters

A parameter list is a comma-separated sequence of typed binders. Consecutive parameters with the same type may share it: (A B : U0, x y : A) means (A : U0, B : U0, x : A, y : A). Later parameter types can mention earlier parameters, as x : A does here. A declaration with parameters is a function, so same(Nat, 0) has type Nat and same(Nat) is a function Nat -> Nat.

def flip_arguments(A B C : U0, f : A -> B -> C) : B -> A -> C {
  intro b a;
  exact f(a, b);
}

A proof's statement can go either in its parameters or in its result type. def t(x : A) : P(x) { … } and def t : forall x : A, P(x) { intro x; … } check the same function type. Parameters are shorter. A result type is better when the statement is a named proposition you want to reuse.

exists is an actual dependent pair with a witness. It is not automatically truncated. Likewise, or retains its choice of summand. Use propositional truncation when you mean mere existence.

Propositions are types, and a proof of a proposition is an element of it. A -> B is implication, A and B conjunction, A or B a disjunction that records which side holds, and A -> Void negation. There is no separate sort of propositions. IsProp(A) is a library definition saying that A has at most one element up to equality.

Universes

U0 denotes U₀; U1, U2, and U3 denote U₁, U₂, and U₃. In particular U0 : U1. Smaller types can be lifted to larger universes; a larger type cannot be silently lowered.

def large_identity(A : U1, x : A) = x;
def lifted_unit = typed(U1, Unit);
def identity(U : Universe, A : U, x : A) = x;
def small_identity = identity(U0);
def universe_identity = identity(U2, U1, U0);

A declaration with A : U0 remains restricted to small types. Write U : Universe to parameterize a declaration over a universe. This makes the declaration a template: the elaborator makes a separate, specialized copy for each universe it is used at, and the kernel checks that copy. The argument must be a universe, not an arbitrary type. Universe arguments are explicit; the compiler does not infer them. Several universe parameters can be grouped, as in (U V : Universe, A : U, B : V). A family may need an explicit lift, such as fun (a : A) => typed(U1, Unit).

When inspecting a universe template, choose U0, U1, U2, or U3 for each universe parameter. The inspector checks that specialization and shows its expression, type, and local context. Names inside the template use the selected universes too. Workbench transfers preserve the selection and display names such as GroupAt_U0; the generic declaration remains a template.

IsProp(A), IsSet(A), and Equiv(U, A, B) are library definitions, not new sorts or language keywords. In particular, IsSet(A) says that any two identity proofs between the same elements agree.

Terms and notation

x =[T] y is equality with an explicit carrier: both endpoints must have type T. Plain x = y infers that carrier. This is an identity type, not an assertion of definitional equality or a cast.

def explicit_reflexivity(U : Universe, A : U, x : A) : x =[A] x {
  exact refl(x);
}

Application and functions

Application is curried: f(a, b) means f(a)(b), and f(a) alone is a valid partial application. fun (x : A) => body constructs a function. Binders can be grouped in the same way as parameters:

SourceMeans
fun (x y : A) => bodyfun (x : A) => fun (y : A) => body. The shared domain is checked once, before either name is bound.
fun (a : A) (b : B) => bodySeparate binder groups with different domains. Use separate parentheses, not commas.
fun x => bodyThe domain is taken from the expected function type. It needs one, from a signature, an exact goal or typed.
 
def constant(A B : U0) = fun (a : A) (b : B) => a;

def compose(A B C : U0) : (B -> C) -> (A -> B) -> A -> C {
  exact fun g => fun f => fun x => g(f(x));
}

In compose, each untyped binder reads its domain from the goal: g : B -> C, f : A -> B, x : A. Without an expected type, such as in def k = fun x => x;, elaboration reports “Untyped lambda requires an expected function type.” More untyped binders than the expected type has arguments are also rejected.

Pairs, sums and expected types

Parentheses group expressions. The kernel uses binary pairs. Tuple notation (a, b, c, d) expands to (a, (b, (c, d))). Explicit left-nesting stays distinct: ((a, b), c) is a different shape. Pass a tuple as one argument with f((a, b, c)); f(a, b, c) remains curried application.

def two_units = typed(Unit and Unit, (tt, tt));
def choose_left = typed(Unit or Nat, left(tt));

typed(T, term) checks term against T. Pairs and sum injections need an expected type. A pair (a, b) could inhabit A and B or many different exists types, so the elaborator cannot guess it. A typed theorem, a have block, or typed supplies it. left, right, and absurd are introductions/elimination checked against that expected type.

Arithmetic

Arithmetic operators +, *, <, and <= are for Nat and use the arithmetic library (normally import primes;). They are not overloaded field operations. They denote add, mul, isLt, and le; n < m is le(succ(n), m). Addition recurses on its first argument, so 0 + n computes to n but n + 0 does not. n + 0 = n needs a proof, the library lemma nat_add_zero(n). The inspector’s + for disjoint sum is display notation; write or in source.

Precedence

From tightest to loosest: application, interval application @, *, +, = < <=, and, or, ->. Arrow, and, and or associate to the right; the other infix operators associate to the left. The body of fun, forall, or exists extends through the following expression.

Thus A -> B -> C means A -> (B -> C), and forall x : A, P(x) -> Q(x) means forall x : A, (P(x) -> Q(x)). Do not chain comparisons: write (a < b) and (b < c). Numerals expand to repeated succ, not machine integers. In the source reader, keywords and built-in forms such as sym and succ are purple, named functions are green, and numeral literals, tuple macros and arithmetic notation are amber with dotted underlines. Hover over a macro to see its expansion: 2 shows succ(succ(0)), and a + b shows add(a, b).

W types and binary numbers

W(A, B) is the type of well-founded trees with a label a : A and a child for each b : B(a). Both A and every B(a) are checked types. The universe is the maximum of their universes.

sup(T, a, children) requires T = W(A, B), a : A and children : B(a) -> T. wrec(T, P, step, tree) returns P(tree). Its branch takes a : A, children : B(a) -> T, and ih : forall b : B(a), P(children(b)), then returns P(sup(T, a, children)). At a constructor it computes by applying that branch to the recursive results on the children. These are checked W rules, not axioms or JavaScript recursion.

After import binary_naturals;, a literal such as 0b110 has type BinaryNat and expands to binary_positive(binary_bit0(binary_bit1(binary_one))). 0b0 expands to binary_zero. Leading zeroes do not affect the value. Only digits 0 and 1 are accepted; the parser permits at most 256 significant bits, and the kernel's term-depth resource bound also applies. Digits are stored as text, so there is no machine-number rounding. These literals denote nonnegative numbers; decimal literals still use unary Nat.

binary_add, binary_mul and binary_of_nat are available from binary_arithmetic. Arithmetic symbols are not overloaded. The binary factorial proof and base-2 and base-10 instances compute 10! without a unary expansion of 3628800.

Proof blocks

A block starts with an expected goal type. Each statement either extends the context and continues, or proves the goal and ends the block. Statements that end a block are marked closing below. Nothing may follow a closing statement in the same block. A block that ends without closing its goal is rejected with the remaining goal.

Building the context

intro x; and intro x y h;
Introduce successive arguments of a forall or -> goal. Each type comes from the current goal, including when the goal is a named definition that unfolds to a function type. For a forall x : A, B goal, intro x; binds x : A and leaves B. For an implication P -> Q it binds evidence of P and leaves Q. intro x y h; is three introductions in a row, with the context visible after each one in the inspector.
let name = term;
Name an inferred term in the remainder of the block. The name stands for the term: the checker can see through it by conversion. For an annotation, use let name = typed(T, term);.
have name : T { … }
Prove a local claim in a nested block; then use it as name : T. The nested block can use the surrounding context. Use this to split a long argument into named steps, or to state an equality whose endpoints the elaborator cannot infer.
have name = term;
Name a proof whose type the elaborator can infer, without writing a nested block.
have name : T := term;
Check term against the explicit type T, then name it. This is shorthand for have name : T { exact term; }. The assignment token := keeps an = inside T unambiguous.
obtain (x, evidence) = pair;
Eliminate a dependent pair or product into the remaining goal. Nested and tuple patterns are supported, as in obtain (a, b, c) = triple;. This does not eliminate propositional truncation.

Closing the goal

exact term; (closing)
Check the term against the current goal, using definitional equality where needed, and close the block.
cases term { left x => { … } right y => { … } } (closing)
Prove the current goal in each branch of a disjoint sum. Each branch has its corresponding witness available.
rfl; (closing)
Prove an equality goal whose endpoints are definitionally equal. See equational reasoning.
calc { … } (closing)
Prove an equality goal by a chain of justified steps.
simpa … using proof; (closing)
Simplify the goal and the type of proof, then use proof. See simplification.
over C along p by { … } (closing)
Prove a dependent path goal from an equality after transport. See cubical shorthand.

Changing the goal

These statements transform the goal and continue with the new one. If the new goal is closed by conversion, the block is finished. Otherwise a following statement must prove it.

rw [p, <- q] at lhs occurrence 2;
Rewrite an equality goal with checked equality proofs. See rewriting.
simp;, simp [rules];, simp only [rules];
Rewrite the goal repeatedly with a set of rules. See simplification.
simp [rules] at h as h2;
Add a simplified copy h2 of a local equality h to the context. The goal is unchanged.
ext x;
Turn a goal f = g between functions into f(x) = g(x) for a new x. See function extensionality.
def swap_product(A B : U0) :
    (A and B) -> (B and A) {
  intro pair;
  obtain (a, b) = pair;
  let saved = a;
  have result : B and A {
    exact (b, saved);
  }
  exact result;
}

def swap_sum(A B : U0, value : A or B) : B or A {
  cases value {
    left a => { exact right(a); }
    right b => { exact left(b); }
  }
}

In swap_product, the goal after intro pair; is B and A with pair : A and B in context. obtain replaces pair by its components a : A and b : B. The pair (b, saved) checks against the have type B and A, which also supplies the expected type a pair needs.

Where does setA : IsSet(A) come from?

import sets;

def SetAssumption = forall A : U0, IsSet(A) -> IsSet(A);

def use_set_assumption : SetAssumption {
  intro A;       // A : U0, from the forall
  intro setA;    // setA : IsSet(A), from the implication
  exact setA;
}

The identifier setA is a name chosen by the author; its spelling does not determine its type. The checked goal does. Inspect the named proposition and then the introduced name to follow that dependency.

Induction and case expressions

Natural numbers

def copy(n : Nat) = induction n as k return Nat {
  zero => 0;
  succ previous => succ(previous);
};

def copy_two : copy(2) = 2 {
  exact refl(2);
}

In induction n as k return C(k), the zero branch must have type C(0). In the successor branch, k : Nat is the predecessor and previous : C(k) is the induction hypothesis. The branch must produce C(succ(k)). Each branch is an expression, not a proof block; put a longer argument in a separate helper theorem.

The motive C(k) is what makes this a proof by induction rather than just recursion. For a theorem, it is the statement at k. For example, the library proves n + 0 = n with the motive (k + 0) = k:

def nat_add_zero(x : Nat) = induction x as k return ((k + 0) = k) {
    zero => refl(0);
    succ h => cong((fun (n : Nat) => succ(n)), h);
  };

The zero branch needs 0 + 0 = 0, which holds by computation. The successor branch has h : k + 0 = k and needs succ(k) + 0 = succ(k). That computes to succ(k + 0) = succ(k), which is cong of succ applied to h. When a statement quantifies over further variables, put them inside the motive, as in return (forall y : Nat, …), so the induction hypothesis is general enough.

The function form is induct(n, motive, base, step), with motive = fun (k : Nat) => C(k) and step taking the predecessor and induction hypothesis.

Disjoint sums

def sum_to_nat(value : Unit or Nat) = match value return Nat {
  left unit => 0;
  right n => n;
};

For a result depending on the entire sum element, write match value as z return C(z) { left x => …; right y => …; }. The branch goals substitute left(x) and right(y) for z. The nondependent function form is cases(value, resultType, leftBranch, rightBranch).

Pairs and tuples

def triple(n : Nat) : exists m : Nat, (m = n) and Nat {
  exact (n, refl(n), succ(n));
}
def third : Nat {
  obtain (a, same, b) = triple(0);
  exact b;
}

Tuples with three or more components are macros for right-associated dependent pairs; no extra kernel rule is involved. The same notation works in obtain patterns. Their parentheses are styled as macros: hover to see the binary expansion, or click to inspect the checked expression and type. A tuple needs an expected product or dependent-pair type, just like a binary pair.

npm run linearize:cubist scans the source ASTs and flattens right-nested tuples, preserving comments and explicit left-nesting. It checks that each rewritten source has the identical expanded AST before saving. Use -- --check to report candidates without changing files. The ordinary npm run format:cubist formatter also linearizes tuples automatically.

def first_nat(pair : Nat and Nat) =
  unpack pair as (a, b) return Nat { a; };

unpack has a result type formed outside the new pair variables. Its function form is unpack(pair, resultType, branch), where branch takes both components. obtain provides the corresponding block form.

For a result depending on the original pair, use pair_induction(motive, branch, pair). If pair : exists x : A, B(x), the branch takes x : A, y : B(x) and proves motive((x, y)). Its result is motive(pair). Ordinary obtain does not rewrite occurrences of the original pair in a dependent goal.

Unit and empty types

unit_induction(motive, base, value) proves motive(value) from base : motive(tt). absurd(impossible) eliminates impossible : Void into the expected type. Negation is written A -> Void; there is no not keyword.

Equality and paths

x = y is the identity type, not an instruction to rewrite source text. Its elements are paths. Equality of paths can itself be stated using another identity type. Equality by computation is handled separately by conversion.

Two notions of “equal” appear throughout this page:

  • Definitional equality (conversion): two terms compute to the same normal form, as 0 + n and n do. The checker uses it silently. It is never a proposition you state or prove.
  • Propositional equality: a path p : x = y, a proof that must be constructed, as for n + 0 = n. Using it to replace x by y requires an explicit operation: transport, cong, rw or simp.
OperationRequired data and result

sym, trans, and cong are built into the language and need no import. They construct cubical paths pointwise and add no axiom. The paths library names them inverse, concatenate and similar, and proves their laws, such as trans(p, refl(y)) = p.

def reverse_path(A : U0, x y : A, p : x = y) : y = x {
  exact sym(p);
}

def join_paths(A : U0, x y z : A, p : x = y, q : y = z) : x = z {
  exact trans(p, q);
}

def map_path(A B : U0, f : A -> B, x y : A, p : x = y) : f(x) = f(y) {
  exact cong(f, p);
}

sym also reverses equalities of types: in A =[U] B, the endpoints A and B are types and their carrier is the universe U.

def reverse_type_equality(A : U1, B : U1, p : A =[U1] B) : B =[U1] A {
  exact sym(p);
}

For example, univalence applied to the group structure identity equivalence gives (G =[Group] H) =[U1] GroupIso(G, H). Applying sym gives the orientation used in the highlighted group theorem: GroupIso(G, H) =[U1] (G =[Group] H).

Path induction

The path-induction motive takes x : A, y : A, and p : x = y, and returns a type. The reflexive case base takes a : A and proves motive(a, a, refl(a)). The eliminator returns motive(x, y, p). Informally: to prove something about every path, it suffices to prove it for reflexivity, provided both endpoints are free to vary.

Some inferred pair projections do not retain enough equality information for sym, trans, or cong. Introduce an explicitly typed claim with have p : x = y := term; in that case.

Equational reasoning

Proving an equality with only sym, trans and cong is exact but hard to read: every intermediate endpoint is implicit. The statements below build the same checked paths from a more readable source. Each produces an ordinary proof term that the kernel checks, and in the inspector each links to the term it built.

SituationUse
The two sides compute to the same thingrfl;
You want to show each intermediate expressioncalc { … }
One known equation should replace one specific subtermrw [p];
A few lemmas should be applied everywhere until nothing changessimp only [lemmas];
A hypothesis matches the goal after the same normalizationsimpa only [lemmas] using h;

These tactics act on homogeneous equality goals: x = y with both sides in one fixed type. They do not rewrite a PathP over a varying family. For such goals, see cubical shorthand.

Reflexivity: rfl

import primes;

def two_plus_two : 2 + 2 = 4 {
  rfl;
}

rfl; closes the goal x = y when x and y are definitionally equal. It is exact refl(x); without repeating x. Here 2 + 2 computes to 4. rfl does not prove n + 0 = n for a variable n; that fails with “Type mismatch.” because it needs induction.

Chains: calc

import primes;

def add_zero_twice(n : Nat) : (n + 0) + 0 = n {
  calc {
    (n + 0) + 0 = n + 0 by nat_add_zero(n + 0);
    _ = n by nat_add_zero(n);
  }
}

Each step has the form left = right by proof;. The proof is either a term, followed by ;, or a nested block by { … }, with no semicolon. Inside calc, _ as a left endpoint means the right endpoint of the preceding step. The first left endpoint must match the goal's left side, and the last right endpoint must match the goal's right side, up to conversion. The steps are composed with trans in order.

A nested block starts with that step's equality as its goal, so it can use any tactic:

import primes;

def calc_with_blocks(B : U0, f : Nat -> B, n : Nat) :
  f((n + 0) + 0) = f(n) {
  calc {
    f((n + 0) + 0) = f(n + 0) by {
      rw [nat_add_zero(n + 0)];
    }
    _ = f(n) by {
      rw [nat_add_zero(n)];
    }
  }
}

calc closes the block. It supports only equality chains. Mixed chains such as a < b = c <= d are not available.

Rewriting: rw

import primes;

def rewrite_then_finish(n m : Nat, h : n = m) : n + 0 = m {
  rw [nat_add_zero(n)];   // goal is now n = m
  exact h;
}

def rewrite_second(n : Nat) : (n + 0) + (n + 0) = (n + 0) + n {
  rw [nat_add_zero(n)] at lhs occurrence 2;
}

def rewrite_backwards(n : Nat) : n = n + 0 {
  rw [<- nat_add_zero(n)] at lhs;
}

rw [p]; takes a proof p : a = b and replaces one occurrence of a in the goal by b. Internally it builds cong of a one-hole context around the occurrence and composes it with the goal. <- p uses p right to left, replacing b by a. Several rules rw [p, q, <- r]; are applied one after another, in order.

  • Rules are fully instantiated. Write nat_add_zero(n), not nat_add_zero. rw does not search for arguments; use simp only for that.
  • Which occurrence. Occurrences are counted in preorder (parent before children, left to right) through ordinary function applications. Without at, the count runs across the left endpoint and then the right. at lhs or at rhs restricts it to one side, and occurrence N picks the Nth match; the default is the first. In rewrite_second, the first n + 0 is occurrence 1 and the second is occurrence 2.
  • After rewriting. If the rewritten goal holds by conversion, rw closes the block, and a trailing rfl; would be unreachable. Otherwise the block continues with the rewritten goal, and a following statement must prove it.
  • Where it reaches. Rewriting descends through ordinary applications whose result type stays fixed, such as f(…) and a + …. It does not descend under fun or quantifier binders, into dependent arguments whose type would change, or into the arguments of transport, comp and other cubical forms. A match there is skipped or reported as “Rewrite match occurs in an unsupported dependent position.” Use an explicit cong(fun (x : A) => …, p) instead.

Simplification

The simplifier rewrites with a set of equality lemmas, repeatedly and everywhere it can, until no rule applies. Unlike rw, it accepts lemmas with quantified parameters and works out their arguments by matching. It is predictable rather than clever: it only uses the rules you select or register, never searches arbitrary theorems, and never succeeds by looping or exhausting a budget.

Explicit rule lists: simp only

import primes;

def add_zero_twice_simp(n : Nat) : (n + 0) + 0 = n {
  simp only [nat_add_zero];
}

def residual_goal(n m : Nat, h : n = m) : (n + 0) + 0 = m {
  simp only [nat_add_zero];   // goal is now n = m
  exact h;
}

nat_add_zero has type forall x : Nat, (x + 0) = x. The simplifier finds each subterm of the shape ? + 0, fills x from it, and checks the instantiated rule. As with rw, if the simplified goal holds by conversion the block is closed; otherwise the block continues with the simplified goal.

A rule may be:

  • a quantified lemma name such as nat_add_zero;
  • an instantiated proof such as nat_add_zero(n), or a local hypothesis such as h : a = b;
  • a named simplification set;
  • any of these reversed with <-.

Every quantified parameter must be determined by the matched left side. A rule such as forall x y : Nat, x = x + (y * 0) cannot be used left to right because nothing on the left fixes y. The error is “A simplification rule parameter is not determined by the matched side; supply arguments.” Supply the argument yourself, as in simp only [rule(x, 0)]. Matching is rigid and first-order: a pattern matches a subterm with the same function heads, and it does not unfold definitions to find a match.

Traversal order

The traversal is deterministic, so the same rules always give the same result:

  1. Children are simplified before their parents, and the left endpoint before the right.
  2. At each subterm, rules are tried in the listed order and the first that matches fires.
  3. The pass repeats until no rule applies.

Traversal reaches the same positions as rw: ordinary applications with a fixed result type, not binders or cubical forms.

Commutativity-style rules such as forall x y, x + y = y + x rewrite their own output back into their input. The simplifier detects the repeated state and fails with “Simplification cycle detected in the selected rules.” Instantiate such rules at specific arguments instead, as in nat_add_comm(a, b). There are also fixed resource bounds: 64 rewrites, 512 visited nodes and 8,192 match candidates per traversal, a bound on generated term size, and an elapsed-work deadline. Exceeding any of them is a failure with a named budget message.

Using a hypothesis: simpa

import primes;

def simpa_example(n m : Nat, h : n + 0 = m) : n = m + 0 {
  simpa only [nat_add_zero] using h;
}

simpa [rules] using proof; simplifies both the goal and the type of proof with the same rules. Here both become n = m. It checks that the simplified types match, then reconstructs the original goal from the checked rewrite paths. This saves stating the normalized form of a hypothesis. simpa always closes the block.

Simplifying types, not just equalities

When the goal is a type rather than an equality, simp rewrites the type itself. Each rewrite gives a checked path between types, and the proof of the simplified type is transported back along it:

import primes;

def family_simp(P : Nat -> U0, n : Nat, h : P(n)) : P(n + 0) {
  simp only [nat_add_zero];   // goal is now P(n)
  exact h;
}

def family_simpa(P : Nat -> U0, n : Nat, h : P(n)) : P(n + 0) {
  simpa only [nat_add_zero] using h;
}

def move_type(A B : U0, p : A = B, a : A) : B {
  simpa only [p] using a;
}

In move_type, the rule is a path p : A = B between types, and simpa transports a along it. The simplifier only follows actual paths of types. It will not turn a logical equivalence or a pair of maps between propositions into a rewrite.

Registering rules and sets

import primes;

simp_rule nat_add_zero priority 10;
simp_set nat_units = [nat_add_zero];

def default_rules(n : Nat) : n + 0 = n {
  simp;
}

def named_set(n : Nat) : (n + 0) + 0 = n {
  simp only [nat_units];
}

def simplified_copy(n m : Nat, h : n + 0 = m + 0) : n = m {
  simp [nat_units] at h as h2;   // h2 : n = m
  exact h2;
}

simp_rule name; and simp_rule name priority N; are top-level directives, placed between declarations. They register an already checked equality as a default rule. The priority is an integer from 0 to 1000, with 0 as the default. simp_set name = [a, b]; names a collection of rules. Neither directive creates a new proof rule or an assumption: the registered lemma is rechecked every time it is used.

Registrations and sets are inherited through imports. When modules register the same lemma, it appears once. Defaults are tried in descending priority, then in a fixed order by checked identity. If two imports define different sets with the same name, that name is ambiguous until the current module declares its own set with that name. Registering the same rule or declaring the same set twice in one module is an error.

FormRules used
simp;All default rules in scope
simp [a, s];Default rules plus the listed rules and sets
simp only [a, s];Exactly the listed rules and sets; defaults are ignored
simp without [a];Default rules except a. Cannot be combined with only.
simp [s] at h as h2;The rules of simp [s], applied to the type of the local equality h. Binds the result as h2 and keeps h. A proof statement must follow.
simpa … using proof;Any of the rule selections above, applied to the goal and to proof

Plain simp depends on which rules happen to be registered, so it can change behavior when an import changes. Prefer simp only in library proofs. The inspector can freeze a working simp into a simp only list of the rules that actually fired; see checking and inspection.

Conditional rules

A rule may have hypotheses that matching does not determine. Here zero_if rewrites n + 0 to 0, but only given h : n = 0:

import primes;

def zero_if(n : Nat, h : n = 0) : n + 0 = 0 {
  calc {
    n + 0 = n by nat_add_zero(n);
    _ = 0 by h;
  }
}

simp_rule zero_if priority 20;

def conditional(n : Nat, h : n = 0) : n + 0 = 0 {
  simp with [h];
}

After matching fixes n, the simplifier needs a proof of the premise n = 0. It looks for one in this order:

  1. a local hypothesis listed in with [h, …], which must be a name from the current context;
  2. refl, when the premise holds by conversion;
  3. for an equality premise, simplifying it with the other selected rules. This search goes at most two levels deep and makes at most 64 attempts. A rule cannot be used to prove its own premise.

Every premise proof found this way is checked by the kernel and passed to the rule. If none is found, the rule does not fire, and the error names the blocked parameter and suggests simp with [name]. Only equality premises are solved. Other kinds of hypothesis must be supplied through with.

Cubical paths and pushouts

All Cubist proofs use the Cubical C kernel. A declaration marked “Not checked” has no native certificate.

In cubical type theory, a path p : x = y in A is a function from an abstract interval into A. Its value at 0 is definitionally x and its value at 1 is y. Many path proofs can therefore be written directly, as functions of an interval coordinate, instead of by path induction.

Interval introduces a coordinate inside the forms below. It is not a type in a universe and cannot be used as an ordinary function domain. Coordinates accept 0, 1, flip(i) (the reversal 1 − i), meet(i, j) (minimum) and join(i, j) (maximum).

def reverse_path(A : U0, x : A, y : A, p : x = y) =
  path(fun (i : Interval) => A,
       fun (i : Interval) => at(p, flip(i)));

path(family, body) binds a coordinate in both arguments and constructs a path. at(p, i) evaluates a path at a coordinate. PathP(family, left, right) states a dependent path type: at coordinate i, the path lies in the type family(i). Plain x = y is the case of a constant family. Each family/body is written fun (i : Interval) => ...; their binder names need not agree. The kernel checks the actual family and endpoints.

Shorthand

SourceMeaning
path i => bodypath(family, fun (i : Interval) => body), where family comes from the expected Path or PathP type. Without an expected path type it is rejected.
p @ iat(p, i). Binds tighter than every infix operator except application.

apd_path(f, p)For f : forall a : A, C(a) and p : x = y, the direct dependent path PathP(fun (i : Interval) => C(p @ i), f(x), f(y)), which is path i => f(p @ i).

def reverse_again(A : U0, x y : A, p : x = y) : y = x {
  exact path i => p @ flip(i);
}

def naturality_square(A B : U0, f g : A -> B,
    H : (forall a : A, f(a) = g(a)), x y : A, p : x = y) :
  PathP(fun (j : Interval) => H(x) @ j = H(y) @ j, cong(f, p), cong(g, p)) {
  exact path j => path i => H(p @ i) @ j;
}

reverse_again is the same term as reverse_path above, with the family read from the goal. naturality_square fills a square whose sides are cong(f, p), cong(g, p), H(x) and H(y). The outer path j gets its family from the PathP goal. Each inner path i gets its family from the equality at j. The kernel then checks all four edges.

Dependent paths and transport

def move_in_fiber(A : U0, C : A -> U0, x y : A, p : x = y, v : C(x)) : C(y) {
  exact along C by p from v;
}

def section_path(A : U0, C : A -> U0, f : (forall a : A, C(a)), x y : A, p : x = y) :
  PathP(fun (i : Interval) => C(p @ i), f(x), f(y)) {
  exact apd_path(f, p);
}

def section_via_transport(A : U0, C : A -> U0, f : (forall a : A, C(a)),
    x y : A, p : x = y) :
  PathP(fun (i : Interval) => C(p @ i), f(x), f(y)) {
  over C along p by {
    exact apd(f, x, y, p);   // goal: transport(C, x, y, p, f(x)) = f(y)
  }
}

There are two standard ways to state that a dependent function respects a path. A PathP states it directly, as a path lying over p. The transported equality transport(C, x, y, p, f(x)) = f(y) states it in one fiber. apd_path produces the first; the older apd produces the second. over lets you prove a PathP goal by proving the transported equality, when that is easier. The family C is never inferred: the elaborator does not search for a family that fits.

Function extensionality: ext

def pointwise_path(A B : U0, f g : A -> B, h : (forall x : A, f(x) = g(x))) : f = g {
  ext x;
  exact h(x);
}

Cubical paths make function extensionality provable: path i => fun x => h(x) @ i is a path from f to g. ext x; builds that term. It works for dependent functions too, provided the function type is fixed, meaning the goal is f = g with f g : forall x : A, C(x). It uses no axiom, unlike the FunExt interface.

Composition

comp(fun (j : Interval) => A, at(p, i),
  face(i, 0, fun (j : Interval) => x),
  face(i, 1, fun (j : Interval) => at(q, j)))

comp fills from coordinate 0 to coordinate 1, starting at the supplied base. Optional walls have the displayed face syntax; their coordinate belongs to the outer scope. The kernel checks that the walls match the base and agree on overlaps. With no walls, this is transport. Picture a square with the base as its bottom edge and the walls as its sides. comp produces the top edge. This is how trans is built.

Interval and face formulas are kept in a normal form of joins of meets. Some compact formulas have exponentially large normal forms. Rather than exhaust memory, the checker refuses any expansion beyond 4,096 clauses or a fixed work budget, with a lattice budget error. Split such a proof into smaller named steps.

Pushouts

def P = Pushout(S, A, B, f, g);
// f : S -> A; g : S -> B
// push_left(P, a) : P
// push_right(P, b) : P
// push_path(P, s) : push_left(P, f(s)) =[P] push_right(P, g(s))

pushout_induction(motive, leftCase, rightCase, bridgeCase, value) eliminates a pushout. The motive is a type family over the pushout; the bridge case supplies a dependent path over each gluing path, with endpoints given by the two point cases. Constructor computations are checked in C.

Suspension(A) is the pushout of the two constant maps A -> Unit. north(A), south(A), and meridian(A, a) use its point and path constructors. Open the checked examples.

Suspensions

Suspension is derived from the kernel’s pushout type. Its operations are ordinary definitions in the suspension library. Import suspension_types to use them; click their names to inspect their definitions. Suspension(A) has points north(A) and south(A), and, for every a : A, a path meridian(A, a) : north(A) = south(A). The circle and puncture models build on these operations.

def Suspension(A : U0) = Pushout(A, Unit, Unit,
  fun (_ : A) => tt, fun (_ : A) => tt);
def north(A : U0) = push_left(Suspension(A), tt);
def south(A : U0) = push_right(Suspension(A), tt);
def meridian(A : U0, a : A) = push_path(Suspension(A), a);

suspension_induction(A, C, atNorth, atSouth, coherence, point) eliminates into a family C on the suspension. The coherence argument takes a : A and proves

transport(C, north(A), south(A), meridian(A, a), atNorth)
  = atSouth

The result has type C(point). suspension_meridian_beta(A, C, atNorth, atSouth, coherence, a) gives the propositional computation law on the meridian: dependent application of the constructed section to that path equals coherence(a). See the suspension examples and circle proof.

Axioms and propositional truncation

The operations in this section use explicit universe-specialized axiom schemas. They are explicit dependencies, not consequences of the basic introduction and elimination rules. A user-written axiom declaration is likewise an assumption; its name and dependencies remain inspectable.

Truncation

Truncate(U0, A), often named Mere(A) by the library, expresses mere inhabitation. It discards access to a chosen witness. The inspector can render it as ‖A‖; that is display notation, not source syntax.

Small-universe operationMeaning
Truncate(U0, A)The propositional truncation of A : U0.
TruncateIntro(U0, A, a)Send a : A into its truncation.
TruncateProp(U0, A)Evidence that any two elements of the truncation are equal.
TruncateElim(U0, A, P, proposition, map)Given proposition : forall x : P, forall y : P, x = y and map : A -> P, return Truncate(U0, A) -> P.

For a named universe, use Truncate(U, A), TruncateIntro(U, A, a), TruncateProp(U, A), or TruncateElim(U, A, P, proposition, map). Here U must be a universe such as U1, and both A and the elimination target P must belong to it.

The current library truncation constructor returns a type in U₀ even for larger inputs. These wrappers preserve that signature; they do not assert universe-preserving truncation. In particular, Truncate(U1, U0) is valid, while Truncate(U0, U0) is not.

Function extensionality and univalence

Pointwise equal functions can be proved equal without an axiom using ext. The FunExt interface below remains for existing proofs that were written against it. It is an assumption and is recorded as one.

FunExt(U0, A, B, f, g, pointwise)
For a family B : A -> U0 and dependent functions f, g, turn forall x : A, f(x) = g(x) into f = g.
FunExt(U, A, B, f, g, pointwise)
The explicit-universe form, with A : U and B : A -> U.
Univalence(U0, A, B)
The single axiom: IsEquiv(U1, (A =[U0] B), Equiv(U0, A, B), idtoequiv(U0, A, B)).
idtoequiv(U, A, B, p)
The equivalence induced by a type equality, constructed by path induction without axioms.
ua(U0, A, B, equivalence)
For small types and equivalence evidence in the library’s native equivalence representation, produce A = B. A pair of arbitrary forward and backward maps is not enough.
UnivalenceBeta(U0, A, B, equivalence, x)
Prove that transport of x : A along the univalence path equals the image of x under the equivalence’s forward function.

ua(U)(A, B, e) is the inverse extracted from Univalence(U, A, B). UnivalenceBeta is a derived transport theorem. UnivalenceEta(U, A, B, p) proves ua(U, A, B, idtoequiv(U, A, B, p)) = p. Neither law is an additional axiom. All accept a parameter U : Universe.

Classical principles and choice

LEM(U0, A, doubleNegation)
Uses excluded middle to turn doubleNegation : (A -> Void) -> Void into Truncate(U0, A), for A : U0.
Choice(U)(A, B, setA, setFibers, inhabited)
For A : U, B : A -> U, and inhabited : forall a : A, Truncate(U, B(a)), obtain Truncate(U, forall a : A, B(a)). setA proves that A is a set; setFibers proves it for every fiber. This applies the existing choice axiom at the selected universe. It does not return a selected function outside truncation.

All these interfaces are first-class universe specializations: Choice(U0), FunExt(U1), Truncate(U2) and Univalence(U1) are functions you can name or pass onward. A declared U : Universe also works. Supplying the universe and later arguments together is equivalent: Choice(U0, A, B, setA, setFibers, inhabited).

Universe parameters are specialized by the elaborator before kernel checking. For example, Choice(U0) selects the choice schema at U0; the kernel sees a named context assumption with that specialized signature. There is no kernel application of a generic Choice term to U0. Applying this specialized assumption to A, B, and its remaining arguments does produce ordinary kernel applications. The inspector and workbench show the generic schema, the universe substitution, and the checked instance separately. The generic schema display is explanatory notation, not a checked kernel term.

These are separate dependencies: using truncation or function extensionality does not by itself request excluded middle or choice. Inspect the axiom list on the particular theorem for the dependencies of its checked derivation, including its type and context.

Conversion and opacity

The checker accepts a term when its type is definitionally equal to the requested type. Two terms are definitionally equal when they reduce to the same normal form by these steps:

  • beta: a function applied to an argument computes, so (fun (n : Nat) => succ(n))(0) is 1;
  • delta: a named definition unfolds to its checked body;
  • eliminator rules: induction, match, unpack and similar forms compute on constructors, so 2 + 2 is 4 but n + 0 is stuck on the variable n;
  • eta: a function equals fun x => f(x), and a pair equals the pair of its projections;
  • cubical rules: a path at 0 or 1 is its endpoint, and interval formulas are compared in normal form.

This is why refl and rfl prove some equalities and not others. They succeed exactly when both sides reach the same normal form.

def defines both constructions and proofs. The checker retains named definitions and can unfold their checked bodies to establish equality of types. opaque def is accepted syntax, but currently has the same checking and unfolding behavior as def. Proof blocks appear by name in the inspector, where their bodies can be opened.

opaque def boxed_successor(n : Nat) = succ(n);
def explicitly_opened = unfold(boxed_successor(1));

def opened_is_two : explicitly_opened = 2 {
  exact refl(2);
}

unfold(term) explicitly unfolds definitions and normalizes the term and its type. It can expand a large expression substantially. A theorem such as commutativity is still a propositional equality. The checker never uses a theorem automatically as a rewrite rule. rw and simp use theorems only when they are named in the proof or registered with simp_rule.

In the native cubical backend, with unfolding [name₁, name₂] { expression } scopes selective conversion hints around an expression. The bracketed list contains names of already checked definitions; the braces contain one expression, without a trailing semicolon. Empty lists and nested scopes are allowed. For example:

def identity(n : Nat) = n;
def identity_zero : identity(0) = 0 {
  exact with unfolding [identity] { refl(0) };
}

The checker first tries unfolding the selected wrappers while keeping other definitions folded; ordinary conversion remains available. During elaboration, the hints apply only inside the braces. The compiler may retain the result as a checked helper definition, so the enclosing proof can reuse it without re-expanding it. Rechecking that helper replays its selected strategy; the hints do not leak into surrounding expressions. Hints change reduction order, never the type, assumptions, or proof obligations. They are performance guidance, not evidence of an equality, and do not normalize the whole expression.

Checking and inspection

Open the proof workspace, choose a topic and proof, then use Edit and Check proof (Ctrl/Cmd+Enter). Click a name in Read mode to inspect its type and source. Click a proof-step line number for its goal and local assumptions. A rejected edit leaves the last checked proof available.

The checked kernel details show the expression, its type, and its open context. Folded kernel notation retains names only where their relationship to the stored term is checked. Use the representation selector for Cubist or raw kernel terms; send either term to the workbench to explore reduction and dependencies. Binder grouping, truncation notation, and equality notation change only presentation. Equality notation is enabled by default: (A =[T] B) displays the identity type with endpoints A, B and carrier T. Uncheck it to see Id with the carrier as a subscript instead. Both views retain links to checked definitions.

Inspecting tactics

  • Click calc, rw, simp or simpa to see the checked proof term it constructed. Each by inside a calc links to the path for that step.
  • A simp also shows its rewrite trace: each rule that fired, the checked path it produced, and any premise proofs found for conditional rules.
  • A multi-binder fun opens the whole checked function. Names bound by ext or simp … at h as h2 link to their types like any other local.

Replace with simp only turns a checked simp, simpa or simp at into a simp only list of the rules that actually fired, keeping their original order. Before offering it, the elaborator reruns the simplification with just those rules and requires the same remaining goal and an equivalent proof. After editing, the source is checked again. The action is withheld when it cannot guarantee the same result. This includes when a used imported rule has no name in scope, a set name would shadow a rule name, or premise search would change. It is also withheld for a universe template, because one level's check does not cover the others.

Common errors

Blocks and terms

“intro requires a forall or implication goal”
The next goal is not a function type. Inspect it; a pair needs witnesses, and an equality needs a path.
“A pair needs an expected exists/and type”
Supply a type with typed(T, (a, b)), a theorem signature, or a have block.
“No statements may follow exact or cases”, “Statements after calc are unreachable.”
A closing statement ends the block. Move further reasoning into the appropriate branch, or prove a local claim with have before finishing the outer block.
“Untyped lambda requires an expected function type.”
Give the binder a type, fun (x : A) => …, or put the lambda where a function type is expected.
“This path needs an explicit equality type annotation”
Use have p : x = y := expression; to expose its endpoints to the elaborator.
“Conversion types differ”, “Type mismatch.”
The supplied term does not have the expected type by computation. Check argument order, universes, and dependent endpoints. From rfl, it means the sides are only propositionally equal: use a lemma, rw or simp. A propositional equality may require explicit transport.
An attempted witness extraction from Mere(A) fails
Truncation elimination needs a proposition as its target. Proving mere existence does not in general supply a chosen witness.

Equational reasoning and simplification

“rw left an unresolved equality goal; add a following proof statement.”
The rewrite succeeded, but the new goal does not hold by conversion. Add another rw, an exact, or a simp. The same applies to the simp variants.
“Rewrite occurrence 3 was not found (1 eligible matches).”
Fewer matches exist than the requested occurrence. Check that the rule is instantiated with exactly the subterm that appears, and whether you meant at lhs or at rhs.
“Rewrite match occurs in an unsupported dependent position.”
The only match is under a binder or in a dependent argument. Use an explicit cong with a one-hole function.
“calc step left endpoint does not match the preceding endpoint.”, “calc final endpoint does not match the goal.”
Adjacent steps must share an endpoint up to conversion. Use _ to avoid retyping the previous right side.
“Simplification cycle detected in the selected rules.”
A rule, or a pair of rules, can rewrite a term back to an earlier state; commutativity always does. Instantiate the rule at specific arguments, or remove one direction.
“A simplification rule parameter is not determined by the matched side; supply arguments.”
Matching cannot fix every parameter. Pass the missing arguments explicitly, or use the rule in the other direction.
A conditional rule reports a blocked premise
No proof of the premise was found. List a local proof with simp with [h], or add a rule that proves the premise.
“… budget exceeded.”
Rewriting, matching, term size or elapsed work hit a fixed bound. Narrow the rule list with simp only, or split the proof with have or calc.
“path i => ... needs an expected Path or PathP type.”
Use the long form path(family, body), or place the shorthand where a path type is expected.

Not yet available

Rewriting currently supports homogeneous equality endpoints and type-valued goals through ordinary applications whose result type stays fixed. The following are not available yet:

  • rewriting a hypothesis together with everything that depends on it (simp at makes a new copy instead);
  • apply, refine and sorry;
  • general implicit or named arguments;
  • solving premises that are not equalities;
  • inequality and mixed-relation calc chains.

Library examples

  • Euclid: introductions, local claims, pair witnesses, and sum cases.
  • Paths: identity induction, symmetry, composition, congruence, path i => and apd_path.
  • Primes: natural-number induction with cong, sym and trans, and calc chains.
  • Ring laws and ordered fields: simp only and simpa only on algebraic identities.
  • Group operations: chains of rw.
  • Field extensionality: pair paths built with over.
  • Right inverses of surjections: set assumptions, choice, and mere existence.
  • The circle’s fundamental group: suspension paths, equivalences, and univalence.
  • Complete ordered field interface: explicit universes and constructive hypotheses.
