KERNEL REFERENCE · TO BE WRITTEN

The C kernel

The kernel checks every term the elaborator produces. This reference will describe its terms, its native opcodes and how it checks them.

This page is an outline, to be written. Until then, the language reference explains how source becomes kernel terms, and the kernel workbench shows the native term of any checked declaration.

What the kernel does

The kernel is written in C and compiled to WebAssembly for the browser. It stores terms in an arena of native nodes, each an opcode with a payload and up to four operand handles. It has two halves. The trusted half is the instruction kernel: a declaration enters the registry only by its Define instruction, from a closed judgement derived one typing rule at a time, and only such a definition can be used in another derivation. The other half, the term checker, elaborates: it reconstructs annotations and answers the elaborator’s questions, and nothing it accepts is trusted.

Every native node has one of these opcodes. The operands are the node’s children, in slot order; the payload is the value stored in the node itself. Checking

The term checker checks a term one node at a time, applying one typing rule to each: it infers the node’s type from its operands, extends the context under a binder, and compares types by conversion where they must agree. It elaborates the term the instruction kernel then derives. The Elaboration panels of the language reference show a declaration’s derivation, one rule per step, as the instruction kernel derives it; the term checker’s own trace (cc_kernel_trace_start) stands in if a derivation cannot be shown.

The trace

A caller can ask the kernel to record its actions while it checks a term (cc_kernel_trace_start in kernel/include/cubical_kernel.h). The trace observes the rules and never changes a judgement. The events are:

LineEventRecorded whenOperands

The language reference’s Elaboration panels turn the trace into a forward derivation, in the style of THTH’s proofs. Each INFER event is one application of its node’s rule, completed after the rules for its operands, so the derivation lists judgements in the order they are derived. Each step names its rule and the earlier steps it uses. A comment above the step gives the judgement or context it derives, {n : Nat} ⊢ succ(n) : Nat, over only the part of the context it depends on. An EXTEND event is a CtxExt step, a CONVERT event between types that read differently is a Conv step, and a judgement derived twice is numbered once.

Instructions

The trusted kernel works as THTH did: the caller issues one instruction per typing rule (cc_instr_* in kernel/include/cubical_kernel.h), and the kernel checks it and answers with a judgement. It checks side conditions only by comparing terms up to bound names, and reduces nothing unless an instruction says so, so every search decision, such as how to show two types equal, is made outside the trusted kernel. Every definition is admitted this way: each tactic’s check is derived as the tactic runs, and the declaration’s body when it is defined. An untrusted driver (web/cubical-instruction-driver.mjs) issues the instructions and finds the equality steps; the term checker’s conversion guides its search, within a small budget, but never stands as evidence, and neither do the with unfolding hints, which only steer the term checker. The Elaboration panels and the workbench’s Kernel graph view show these derivations.

A judgement is {Γ} ⊢ t : T, or {Γ} ⊢ a ≡ b : T, over only the context it depends on. Each records the instruction and premises that derived it, and the same instruction on the same premises gives the same judgement, so the judgements form a derivation graph. Identical syntax is likewise one node of the term arena. The steps of a derivation are:

The instructions cover universes, functions, pairs, natural numbers, the unit and empty types, sums, paths at any interval formula, composition, transport, pushouts, W types and Glue, and so every definition in the library and the archive, univalence included.
