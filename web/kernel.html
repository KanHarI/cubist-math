KERNEL REFERENCE · TO BE WRITTEN

The C kernel

The kernel checks every term the elaborator produces. This reference will describe its terms, its native opcodes and how it checks them.

This page is an outline, to be written. Until then, the language reference explains how source becomes kernel terms, and the kernel workbench shows the native term of any checked declaration.

What the kernel does

The kernel is written in C and compiled to WebAssembly for the browser. It stores terms in an arena of native nodes, each an opcode with a payload and up to four operand handles. It is the instruction kernel: a declaration enters the registry only by its Define instruction, from a closed judgement derived one typing rule at a time, and only such a definition can be used in another derivation. Every check goes through it. Until 2026-10-02 the kernel also held an untrusted term checker, whose conversion once guided the search; it was removed, and the search is the driver's alone.

Checking

A term is checked by deriving it: the elaborator's driver issues the instructions that build it, one typing rule per step, and the kernel checks each. The Elaboration panels of the language reference show a declaration's derivation, one rule per step, as the instruction kernel derived it.

Instructions

The trusted kernel works as THTH did: the caller issues one instruction per typing rule (cc_instr_* in kernel/include/cubical_kernel.h), and the kernel checks it and answers with a judgement. It checks side conditions only by comparing terms up to bound names, and reduces nothing unless an instruction says so, so every search decision, such as how to show two types equal, is made outside the trusted kernel. Every term is checked this way: each tactic’s check and each query the elaborator makes is derived as it runs, and the declaration’s body when it is defined. An untrusted driver (web/cubical-instruction-driver.mjs) derives the source syntax itself: it restores annotations, splits composition faces into clauses, and finds the equality steps. The driver’s own guide steers its search, within a small budget, and never stands as evidence. The Elaboration panels and the workbench’s Kernel graph view show these derivations.

A judgement is {Γ} ⊢ t : T, or {Γ} ⊢ a ≡ b : T, over only the context it depends on. Each records the instruction and premises that derived it, and the same instruction on the same premises gives the same judgement, so the judgements form a derivation graph. Identical syntax is likewise one node of the term arena. The steps of a derivation are:

Univalence is built from these.
SignatureBegin, SignatureCons, SignatureCloseDeclared types (H1), on by default since the H1 specification’s release on 2026-10-02. Nat, W and pushouts are ordinary source declarations using these instructions. A signature is admitted one constructor at a time: the former’s type, then each constructor’s type, derived by the other instructions in a context of the signature’s parameters, its sort and its earlier constructors. The kernel checks the normal form on each type as written: data before positions, the sort only at the end of a position or of the result, and boundaries built from earlier constructors and positions. Closing appends the truncation’s squash constructor.
SortBegin, SortLevel, SortParameter, ConIntroAn instance of an admitted declared type: its recorded universe levels first, finite ones, then its parameters, one judgement at a time; the instance lives in the signature’s universe at those levels. An erased universe parameter is read from the universe of the parameter that determines it, and every parameter must then have its telescope type, so a lower parameter is lifted first. ConIntro gives a constructor at a complete instance, its type the declared one with the instance, its levels, parameters and earlier constructors put in. A constructor at an endpoint of one of its dimensions steps to that boundary, by PathBeta, Whnf or Normalize. A data sort composes by its constructors: Comp of one constructor composes its arguments, and transport is a composition. A higher sort, one with a path constructor or a truncation, composes formally by HComp, and Transp moves a constructor along its parameters, correcting its boundary so that transport commutes with each face.
ElimBegin, ElimClause, ElimCloseThe eliminator of a declared type, from a motive over one of its instances and one clause per constructor, the truncation's squash included. Each clause's type is computed from the constructor's, with no reduction: over a path constructor it is a dependent path whose ends are the clauses of its boundary, and each recursive argument brings its displayed hypothesis. The eliminator in progress shows the next clause's type. Iota computes the eliminator on a constructor, at dimensions or not, and Whnf also on a formal composition.

The instructions cover universes and universe-generic definitions, functions, pairs, the unit and empty types, sums, paths at any interval formula, composition, transport and Glue. H1 admits declared types, forms their instances and constructors, composes and transports them, and eliminates them. Natural numbers, W trees and pushouts use those shared rules.
