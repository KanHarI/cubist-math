The C kernel

The kernel checks every term the elaborator produces. This reference will describe its terms, its native opcodes and how it checks them.

This page is an outline, to be written. Until then, the language reference explains how source becomes kernel terms, and the kernel workbench shows the native term of any checked declaration.

What the kernel does

The kernel is written in C and compiled to WebAssembly for the browser. It stores terms in an arena of native nodes, each an opcode with a payload and up to four operand handles. It accepts a declaration only when its term has its stated type, and it is the only part of Cubist that is trusted.

Opcodes

Every native node has one of these opcodes. The operands are the node’s children, in slot order; the payload is the value stored in the node itself. Checking a node applies one typing rule, named here as in THTH, the forward proof engine this kernel descends from. The remaining rules are still to be written.

Checking

The kernel checks a term one node at a time, applying one typing rule to each: it infers the node’s type from its operands, extends the context under a binder, and compares types by conversion where they must agree. The Elaboration panels of the language reference show every rule it applied to a declaration, from the kernel’s own trace (cc_kernel_trace_start).

To be written: the typing rule of each opcode, and the steps the kernel counts.

The trace

A caller can ask the kernel to record its actions while it checks a term (cc_kernel_trace_start in kernel/include/cubical_kernel.h). The trace observes the rules and never changes a judgement. The events are:

LineEventRecorded whenOperands
INFERCC_TRACE_INFER, CC_TRACE_INFERREDThe checker applies the typing rule of a node (ck_infer). The events for its operands follow, one level deeper, and the line ends with the type found.the node; the checked node and its type
REUSEDCC_TRACE_REUSEDA node was already checked in the same context, and its judgement is reused.the node, the checked node and its type
EXTENDCC_TRACE_EXTENDThe context gains an assumption, on entering a binder (ck_extend).the bound symbol and its type
CONVERTCC_TRACE_CONVERTA type found must be convertible to, or cumulative with, the type expected (ck_expect).both types, and whether they agree
REDUCECC_TRACE_REDUCEA term is reduced to weak head normal form, unfolding definitions, and changes (ck_whnf). Reductions inside a conversion are not recorded.the term and its weak head normal form

The language reference’s Elaboration panels turn the trace into a forward derivation, in the style of THTH’s proofs. Each INFER event is one application of its node’s rule, completed after the rules for its operands, so the derivation lists judgements in the order they are derived. Each step names its rule and the earlier steps it uses. A comment above the step gives the judgement or context it derives, {n : Nat} ⊢ succ(n) : Nat, over only the part of the context it depends on. An EXTEND event is a CtxExt step, a CONVERT event between types that read differently is a Conv step, and a judgement derived twice is numbered once.
